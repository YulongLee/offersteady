## Context

管理端目前存在三套相关但割裂的数据：即时总览、按自然日保存的运营趋势快照、以及订单/回调明细。“实收金额”卡片来自日快照，而支付是否入账只认本地订单 `paid` 状态；当支付宝已收款但通知校验失败时，系统没有把渠道事实、待恢复金额和失败环节连起来。服务器侧已有容量采样，可显示部分容器 CPU/内存、数据库连接和 API 指标，但缺少独立入口、磁盘/运行时长/依赖健康与可操作的状态解释。

本变更涉及 Backend、Admin、PostgreSQL 迁移和生产运维。支付数据属于财务数据，恢复订单必须保持现有的渠道权威查询、响应验签、金额一致和幂等账本边界。服务器监控必须保持低权限和有界开销，不能通过 Docker Socket 或任意主机文件读取扩大攻击面。

## Goals / Non-Goals

**Goals:**

- 让运营人员立即看到今天本系统已确认入账的订单金额、待确认金额和异常回调金额，并理解它与历史趋势的不同口径。
- 把支付宝通知失败拆成可诊断的签名、AppID、Seller ID/PID、金额、订单和交易状态结果。
- 复用现有支付宝权威查单能力，提供可审计、幂等、逐笔执行的安全对账恢复。
- 提供独立服务器监控页面，展示应用资源、磁盘、运行时、数据库、Redis、分析任务和 API 质量。
- 保证所有新增查询有权限、时间范围、超时、脱敏和失败隔离。

**Non-Goals:**

- 不提供跳过渠道验证的“手工设为已支付”或直接修改积分/会员汇总。
- 不把支付宝同步返回页当作支付成功依据，不自动信任用户截图或渠道后台截图。
- 不实现 Prometheus/Grafana、跨多主机基础设施平台、短信告警或自动扩缩容。
- 不挂载 Docker Socket，不展示环境变量、密钥、进程命令、完整渠道交易号、用户资料或面试内容。
- 不修改用户 Web 支付流程和桌面助手。

## Decisions

### 1. 将实时支付摘要与历史趋势明确分层

新增受 `payments.read` 或 `observability.read` 保护的实时支付摘要查询，直接对 `billing_checkout_orders` 和脱敏回调结果做有界的当日聚合，时区固定为 `Asia/Shanghai`。返回已入账、待确认、异常、已关闭的订单数与金额以及生成时间。历史折线仍读取每日快照，页面明确标注“实时”和“日结趋势”。

选择直接聚合权威订单表而不是每次刷新日快照，是因为当日订单量可控且已有查询超时/并发预算；它避免把尚未结束的自然日固化成误导快照。替代方案是请求时重算今日全部指标，但会扩大数据库开销并混淆历史口径，因此不采用。

### 2. 支付校验结果拆分保存为安全分类

扩展支付通知解析和事件持久化，分别记录 `signature_verified`、`app_identity_verified`、`seller_identity_verified`、`amount_matches`、`order_known` 与最终 `outcome`。只保存布尔值、安全错误码、订单引用和时间，不保存通知原文；历史事件保持兼容，未知维度显示“历史未采集”。

支付宝配置页只接受支付宝官方定义的签约商户 PID：以 `2088` 开头的 16 位纯数字。静态格式校验用于阻止明显错误的卖家账号进入“配置可启用”，真实通知/主动查单结果仍是最终验收证据。保存有效格式不代表链路通过；格式错误时必须保持渠道关闭并给出可操作提示。

### 3. 对账只走权威主动查单并逐笔确认

复用 `alipay.trade.query`：服务端签名请求、验证支付宝响应签名、核对订单号、金额与成功状态，再调用现有幂等 `confirm_checkout_paid`。管理端展示候选订单和“权威查单”操作；操作需要 `payments.reconcile`、近期 MFA、原因和幂等键，并记录审计。失败只返回安全状态，不发放权益。

首版不做自动批量补单。相比后台定时自动恢复，逐笔操作更适合当前原型阶段和少量真实订单，能降低错误配置造成批量误入账的风险。后续在真实数据量增长后再评估受限自动对账。

### 4. 服务器监控采用应用内只读采样

新增 `ServerHealthService`，从允许来源采样：

- Linux `/proc` 与 cgroup：应用实例 CPU、内存限制/使用、系统负载和运行时长；读取失败标记不可用。
- `shutil.disk_usage`：应用挂载卷/根文件系统的总量、已用量和使用率，不枚举目录或文件。
- PostgreSQL：受限连接检查、连接使用量和查询延迟。
- Redis：PING、内存摘要和连接状态，不读取键值。
- 现有容量/API 指标与分析任务健康：P95、错误率、最后成功聚合时间。

后端接口返回当前快照和最近 60 分钟聚合点，采样独立执行并设置超时。容器“健康”以应用和依赖探针表示，不访问 Docker daemon。替代方案是挂载 `/var/run/docker.sock` 读取容器列表，但这等价于向应用授予高权限控制面，安全风险不可接受。

### 5. 管理端按任务组织而不是堆叠更多卡片

运营总览顶部新增实时支付摘要与异常提示；订单页增加“待对账”筛选和逐笔诊断；支付设置显示渠道验收状态；新增“服务器监控”导航页展示资源、依赖和最近曲线。每个区域都有加载、过期、不可用和重试状态，后台其他页面不因单个监控接口失败而不可用。

## Risks / Trade-offs

- [风险] 实时聚合查询增加数据库压力 → 仅查询当天、有索引字段，限制刷新频率、超时和并发，并增加查询回归测试。
- [风险] 通知验证维度迁移导致历史数据含义混淆 → 新字段可空，历史显示“未采集”，不推断历史失败原因。
- [风险] 权威查单成功但权益重复发放 → 复用订单行锁、唯一渠道交易号、账本引用唯一键和会员订单唯一键。
- [风险] 监控采样因容器环境差异失败 → 每个采集器独立降级，返回 `unavailable`，不让整体接口或用户请求失败。
- [风险] 管理页面暴露基础设施细节 → 只返回标准化指标、服务别名和安全错误分类，继续要求 `observability.read`。
- [风险] 今日实时值与历史趋势短暂不同 → 页面明确标注实时/日结口径和更新时间，次日快照完成后自然收敛。

## Migration Plan

1. 增加可空的支付诊断字段/表迁移，部署后仍兼容旧 Backend。
2. 在管理入口保持开启的前提下先部署 Backend，验证旧管理 API、支付通知和用户支付不受影响。
3. 使用合成回调测试各诊断结果；使用内部已支付测试订单验证主动查单只在完整校验后入账。
4. 部署 Admin，灰度开放实时支付摘要、待对账队列和服务器监控。
5. 对当前已由支付宝权威查单确认的两笔订单逐笔执行对账，核对账本/会员权益与实时实收金额。
6. 观察数据库查询延迟、管理 API 错误和资源采样至少一个调度周期后完成验收。

回滚时先回滚 Admin 隐藏新入口，再回滚 Backend；新增可空字段和诊断数据保留。不得通过回滚删除已验证入账的订单或权益流水。

## Open Questions

无。首版按单机生产环境、逐笔支付宝对账和应用内安全采样实施；多主机监控与自动对账另立变更。
