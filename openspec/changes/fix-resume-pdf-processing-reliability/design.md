## Context

简历上传采用“上传完成后异步处理”的链路：Web 端完成 OSS 上传并创建处理任务，后台 Worker 调用 MinerU/文档解析器，再写入标准化 Markdown 和文档可用状态。当前上传请求本身通常很快，但完整处理可能需要十几秒；Web 端的有限轮询窗口与后台处理耗时接近，导致页面提前停止刷新。另一方面，解析器或对象存储的可恢复失败会把处理任务放回队列，但持久化作业达到重试上限后可能已经失败，文档仍保持 processing，形成状态不一致。

本变更只处理 PDF/简历资料的可靠性，不改变上传接口、资料权限、桌面伴随程序或 AI 提示词。简历内容仍按敏感资料处理，日志只记录任务 ID、阶段、耗时和安全错误码。

## Goals / Non-Goals

**Goals:**

- 让 Web 端持续等待到明确的完成或失败状态，而不是因轮询窗口结束误报未解析。
- 让解析任务、持久化处理作业和文档状态在成功、重试耗尽、删除和读取失败时保持一致。
- 对 MinerU 无效结果和对象存储临时读取失败执行有限、幂等的重试。
- 为慢解析、解析失败、重试耗尽和前端终态刷新增加回归测试。

**Non-Goals:**

- 不更换 MinerU 或聊天模型供应商。
- 不支持新的文件格式，不改变现有 PDF/DOCX/DOC/TXT/MD 白名单。
- 不把处理改成同步请求，不在客户端保存或上传服务端密钥。
- 不处理 API P95、容器内存或桌面伴随程序轮询问题。

## Decisions

### 1. Web 端采用更长的有限轮询窗口

上传完成后以 2 秒左右的间隔查询资料状态，最长等待 90 秒；遇到 `ready`、`failed`、`deleted` 或 `disabled` 立即停止。90 秒仍未终态时显示“后台仍在处理，可稍后刷新”，不伪造失败。

替代方案是无限轮询，会造成页面卸载后请求泄漏和无休止请求；也可以引入 SSE，但当前资料处理量和产品阶段不值得新增连接协议。

### 2. 失败状态以处理任务为事实源并统一收敛

解析器失败先保存安全错误码和失败事件；若仍可重试，任务和持久化作业都进入可调度的 retrying 状态；达到上限后，任务、作业和文档统一进入 FAILED/failed，并写入完成时间。不会让“任务 QUEUED、作业 failed、文档 processing”长期共存。

替代方案是仅修改前端文案，这会掩盖后台状态不一致，无法支持重试和运营排查。

### 3. 只重试可恢复错误

`parser_invalid_result`、`object_load_failed`、解析供应商超时/临时不可用属于可恢复错误，最多重试两次，并使用现有持久化 job 的幂等 task ID。格式不支持、空文档、解码失败和文档已删除直接失败。

替代方案是所有异常都重试，会把坏文件和供应商永久错误放大为队列负载。

### 4. 对解析结果做最小有效性校验

保存 normalized Markdown 前必须确认结果非空且能被 Markdown 归一化器接受；无效结果不能标记为 ready。原始简历文本不写入日志。

## Risks / Trade-offs

- [Risk] 轮询窗口变长会增加单个上传页面的请求次数 → Mitigation: 只在上传后的短窗口轮询，终态立即停止，页面关闭时取消请求。
- [Risk] 供应商持续异常时重复重试增加成本 → Mitigation: 限制最多两次，错误按类型区分，失败后提供手动重试。
- [Risk] 旧任务状态已经不一致 → Mitigation: 新逻辑保证新任务收敛；部署后只读扫描旧任务并在后续维护任务中单独修复，不在本次发布中直接删除用户资料。
- [Risk] PDF 扫描件或加密件仍可能无法解析 → Mitigation: 明确显示文件原因，不把失败伪装成空简历。

## Migration Plan

1. 本地实现状态收敛、重试和 Web 轮询改动，并补充回归测试。
2. 在无用户进行面试时部署国服，保持旧 API 请求格式兼容。
3. 部署后用合成 PDF 做一次上传、完成和失败重试验证，再观察处理任务状态。
4. 若出现回归，回滚应用镜像；不删除 OSS 原文件或数据库资料。

## Open Questions
