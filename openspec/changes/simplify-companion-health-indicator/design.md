## Context

当前 renderer 同时使用“当前是否存在面试 binding”和“最近是否检测到真实音频信号”决定状态灯颜色。因此，设备已经登记并在线、但尚未进入面试或音频暂时静音时，会显示与真实故障相同的红色。内部状态仍需要保留给采集、重试和诊断逻辑，但用户不需要感知这些阶段。

## Goals / Non-Goals

**Goals:**

- 让正常待机、正常面试和短暂自动恢复统一显示绿色。
- 只在已确认、需要用户处理的网络、权限或设备故障时显示红色。
- 保留真实音量反馈，不用动画伪造音频输入。
- 通过纯状态映射和回归测试避免触碰稳定的实时音频链路。

**Non-Goals:**

- 不改变音频采集源、帧大小、发送频率、WebSocket、ASR 或字幕逻辑。
- 不改变面试 session binding、设备登记或自动重试协议。
- 不调整现有窗口布局、按钮结构或权限申请流程。
- 不重建与本次桌面下载清单无关的服务，不修改数据库、Redis 或生产业务配置。

## Decisions

### 1. 将内部运行状态映射为独立的用户健康状态

新增纯函数统一派生 `healthy` / `fault`。设备已登记且没有确认故障时视为健康；缺少当前面试 binding 不再视为故障。保留原有详细状态给内部逻辑和诊断使用。

替代方案是直接修改现有 capture state。该做法会影响采集与恢复分支，风险超出本轮视觉优化范围，因此不采用。

### 2. 音频通道可用性与当前是否有声音分离

已打开、静音、接收中和短暂重连的音频通道均使用绿色状态灯；音量条仍只按真实 level 展示。权限拒绝、平台不支持或来源不可用才使用红色。

替代方案是让静音状态灯跟随信号 freshness。该方案正是待机时误报红色的来源，因此不采用。

### 3. 自动恢复期间不打扰用户

短暂重连保持绿色；只有现有运行状态已经进入明确 error，或来源诊断为权限拒绝/不可用时才显示红色。本变更不修改重试次数或失败阈值。

替代方案是增加黄灯或蓝灯表示中间态。用户已明确要求减少颜色和状态感知，因此不采用。

### 4. 版本号统一升级到 1.2.12

更新 desktop workspace 的 package 版本及根 lockfile 对应条目，确保窗口标题和本地包名称一致。

## Risks / Trade-offs

- [Risk] 短暂重连保持绿色可能减少技术状态可见性 → 内部状态和诊断日志继续保留，确认失败后仍转红。
- [Risk] 静音通道显示绿色可能被误解为正在收到声音 → 音量条不伪造波动，文案保持“等待声音/通道可用”的真实语义。
- [Risk] 状态映射散落会再次产生不一致 → 用一个纯函数作为入口状态与来源状态的共同语义基础，并覆盖回归测试。

## Migration Plan

1. 新增健康状态映射与单元测试。
2. 替换现有绑定灯和来源灯的二元判断，保持布局不变。
3. 升级版本并运行 typecheck、desktop tests、build 与 OpenSpec strict validate。
4. 构建 arm64 本地包并启动，完成用户验收。
5. 生成并验证两种 macOS 正式 DMG 与 Windows x64 安装包，先上传不可变 OSS 对象，再原子更新下载清单。
6. 提交并推送发布清单，在生产服务器只重建 Backend 下载清单消费者；数据库、Redis、Web 和 Admin 保持不变。
7. 如线上验收异常，恢复上一个桌面发布清单并重建 Backend，不删除任何版本化产物或用户数据。
