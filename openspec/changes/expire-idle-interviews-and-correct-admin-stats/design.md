## Context

`interview_sessions.status='live'` 当前只有显式结束面试时才会改变。关闭浏览器、断网、助手退出和软删除不会可靠结束会话，管理后台又只按状态计数且不排除 `deleted_at_ms`，因此生产环境出现大量伪活跃记录。系统已经记录 `last_activity_at_ms`、实时发布通道、设备绑定及回答任务状态，可以在不保存额外敏感数据的前提下建立统一活跃口径。

## Goals / Non-Goals

**Goals:**

- 每个用户最多保留一场真实活跃面试。
- 连续 20 分钟没有有效业务活动且无处理中任务时自动结束。
- 用户在第 18 分钟收到提示并能继续面试。
- 后台总览和列表展示同一份真实生产状态。
- 安全归档现有陈旧会话并释放关联实时资源。

**Non-Goals:**

- 不按积分余额或实际扣点值判断活动。
- 不删除历史面试、转录、回答、积分流水或审计数据。
- 不改变实时 ASR、回答模型、收费标准和页面原型。
- 不把普通 HTTP 页面轮询或后台读取视为面试业务活动。

## Decisions

### 1. 使用服务端权威业务活动时间

会话的 `last_activity_at_ms` 仅由有效音频帧、手动回答提交、截图回答提交、用户确认继续和开始面试更新。选择该方案而不是“积分变化”，因为会员使用可能扣除 0 点；也不使用普通页面心跳，避免无人页面永久保活。

### 2. 采用两阶段空闲生命周期

服务端返回剩余空闲时间；前端在 18 分钟时展示非阻塞提示，20 分钟后由服务端原子结束。处理中回答或截图任务构成关闭保护，任务结束后重新按最后业务活动计算。服务端判定是权威结果，前端计时只负责体验提示。

### 3. 统一管理后台活跃分类

“真实活跃”要求：未删除、状态为 `live`、最后业务活动在 20 分钟内，并且存在近期页面/设备/发布活动之一。“空闲待关闭”是状态仍为 `live` 但已超时；其余展示数据库生命周期状态。总览和列表复用同一 SQL 口径。

### 4. 使用幂等回收操作

自动回收复用现有结束面试和实时资源释放领域命令，重复执行不产生额外副作用。部署时先上线新查询和回收逻辑，再批量归档上线前已超时的会话。

### 5. 数据库约束只覆盖非删除 live 会话

清理历史重复记录后增加每用户至多一条未删除 `live` 会话的部分唯一索引，防止并发请求绕过应用层冲突检查。若迁移前仍有冲突则迁移失败并停止，不静默删除数据。

## Risks / Trade-offs

- [长时间只观看但不操作的用户被关闭] → 音频帧属于有效活动，并在第 18 分钟允许手动继续。
- [客户端时钟不准确] → 所有截止时间由服务端时间计算，客户端只渲染。
- [处理中任务超过 20 分钟] → 任务保护阻止关闭，但设置有限保护窗口并记录异常任务。
- [批量归档误伤真实会话] → 仅处理超过阈值且没有近期连接、发布或处理中任务的记录。
- [唯一索引与旧数据冲突] → 先生成审计报告并完成幂等归档，再创建索引。

## Migration Plan

1. 部署统一活动刷新、空闲分类和后台查询，不立即清理数据。
2. 运行只读报告，核对待归档会话数量及最近活动时间。
3. 幂等结束满足条件的陈旧会话并释放绑定、发布通道。
4. 创建每用户单一未删除 `live` 会话的部分唯一索引。
5. 启用周期性空闲回收和用户端 18 分钟提示。
6. 回滚时可停止回收任务并回退查询；已归档会话保留在历史中，不恢复为 `live`。

## Open Questions

无。首版固定使用 18 分钟提示、20 分钟自动结束，后续通过服务端配置调整。
