## Context

生产采样显示普通 API P95 会从约 300 ms 上升到 0.8–10 s。控制面请求可达约 466 次/分钟，其中设备连接、设备心跳和失效截图绑定占绝大多数。当前 `RedisRealtimeSpeechRepository._write` 对设备或网页心跳这样的单实体更新也会持有全局锁、序列化并 `SET` 约 1.18 MB 的全局快照，再 `HSET` 全部会话活动版本。部分 `async` 路由直接调用同步仓库；单 Uvicorn worker 因此把一次昂贵写入扩散成全局排队。

当前 Redis 仓库仍保留进程内权威视图，因此本变更不能通过直接增加 worker 解决。旧桌面版本仍在线，服务端也不能依赖所有用户先升级。现有全局快照还必须保留作兼容与回滚来源。

## Goals / Non-Goals

**Goals:**

- 让高频设备心跳、网页心跳和活动版本更新只写当前实体，不再重写全局快照。
- 保持单 worker 下现有进程内一致性语义，并让重启后可从实体状态覆盖旧快照恢复。
- 将重复控制查询的昂贵计算限制为每个设备一个短时结果，同时保留正常绑定发现速度。
- 隔离短时同步 Redis 控制操作，避免阻塞异步事件循环。
- 保持所有公开 API、状态码、SSE/WebSocket 协议及产品行为兼容。
- 使用当前提交和生产镜像作为可验证回滚基线。

**Non-Goals:**

- 不完成全部运行态的会话分片或删除旧快照。
- 不增加 Uvicorn worker，不引入新服务或新数据库。
- 不修改 ASR、音频、字幕、快答、截图生成、Prompt、计费、UI 或桌面权限。
- 不强制旧桌面版本升级，也不以 429 限流改变客户端状态机。

## Decisions

### 1. 高频易失状态使用旁路实体 Hash，语义状态继续兼容旧快照

新增版本化 Redis Hash 保存 `devices`、`device-code-index`、`web-heartbeats` 和 `active-web-by-user`。设备与网页心跳在进程内完成现有状态转换后，只通过 Pipeline 更新对应 field 和 TTL。活动版本只更新当前 `session_id` field。

仓库启动时先加载旧快照，再用实体 Hash 中更新的数据覆盖；若实体 Hash 为空，则从旧快照幂等补齐。旧快照在本轮不删除，绑定、账户设备和候选等低频语义写入暂时沿用原兼容持久化，确保旧镜像回滚仍能恢复关键状态。

替代方案是一次迁移全部实时对象到每实体 Key。它更彻底，但会同时改变绑定、候选、字幕和恢复路径，超出今天 P0 的风险边界。

### 2. 保持现有状态机，单独提供增量写帮助函数

不复制设备、租约 generation 和单活动页面选择规则。新帮助函数仍调用 `InMemoryRealtimeSpeechRepository` 的既有实现，只替换持久化步骤。需要排他性的 live page claim 使用按用户 Redis 锁；设备心跳只需进程锁和原子 Pipeline。

替代方案是重新实现 Lua 状态机。它有利于多 worker，但会在本轮引入双重业务语义，故推迟到完整外置阶段。

### 3. 重复控制查询使用亚秒级 single-flight/缓存，不使用破坏性限流

以设备、机器码和 pinned binding 为键复用短时间内相同连接查询结果，缓存上限小于服务端现有 `refreshAfterMs=1000`。绑定建立、设备 generation 变化或缓存到期后立即重新计算。失效截图资格保持现有 404/错误码，但内部查找复用轻量结果，并对重复诊断日志采样。

替代方案是对客户端返回 429。旧客户端可能把 429 视为产品故障或立即重连，因此不采用。

### 4. 短同步仓库工作使用独立有界执行器

高频 HTTP 控制路由通过专用短任务执行器调用同步服务；现有 Redis Stream 阻塞等待继续使用事件等待执行器。两者的 worker、队列和超时独立。WebSocket 音频热路径、ASR worker 和模型调用不进入该执行器。

替代方案是立即全面迁移到 `redis.asyncio`。长期应采用，但本轮会扩大所有仓库接口和生命周期管理的修改面。

### 5. 以无活跃面试门禁和蓝绿切换保护生产

候选镜像先在无生产流量下启动并验证。只有活跃面试、活跃音频流均为零时才切换入口；旧容器与旧 Redis Key 保留至观察窗口结束。任何核心指标或业务回归立即切回基线镜像。

## Risks / Trade-offs

- [实体 Hash 与旧快照短时不一致] → 启动时以实体 Hash 的较新时间戳/generation 覆盖，旧快照只作缺失回落；关键语义变更继续写兼容快照。
- [短缓存延迟发现新绑定] → 缓存期限严格小于 1 秒，并在本进程创建绑定时主动失效。
- [线程池并发放大仓库争用] → 使用专用有界执行器，并先消除大快照写入；压测验证队列和超时。
- [回滚后易失心跳较旧] → 旧客户端会在既有心跳周期内重新刷新；绑定、候选和正式会话数据不丢失。
- [旧客户端仍产生网络请求] → 服务端将每次请求成本降为 O(1) 小读写；客户端退避升级作为后续发布，不作为本次正确性依赖。
- [双结构增加短期维护成本] → Key 带版本和指标，观察稳定后再通过独立变更删除旧快照。

## Migration Plan

1. 记录 Git 基线 `dfc3ca8` 和当前生产镜像，禁止覆盖。
2. 在本地实现实体状态、兼容覆盖、短缓存和执行隔离；默认配置可关闭新路径。
3. 使用合成数据验证旧快照恢复、实体覆盖、重复心跳、live page claim、失效绑定和并发请求。
4. 执行完整后端回归、OpenSpec strict 校验和控制面压力测试，确认 ASR/字幕/回答/计费无行为变化。
5. 构建候选镜像；生产只读确认活跃面试与音频流为零。
6. 启动候选后端并完成健康、Redis、PostgreSQL与核心 API 探针，再切换入口。
7. 观察至少 30 分钟：API P95/P99、CPU、Redis 写入带宽、5xx、重连、字幕与回答错误。
8. 若不满足门槛，立即切回基线入口/镜像；旧容器与旧 Key 保留，不删除数据库或 Redis 数据。
