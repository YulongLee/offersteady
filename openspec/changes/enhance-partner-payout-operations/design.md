## Context

国内合作伙伴计划已经具备推广链接、20% 订单级佣金账本、退款冲正和月度人工结算状态机。产品确认活动入口只应位于官网首页底部，不进入登录后的工作台导航；结算申请没有收款目标；管理后台只展示合作伙伴汇总和结算申请，无法按订单与账本状态完成日常对账，也缺少活动启停开关。

支付宝账号、微信账号和实名姓名属于敏感个人信息。现有设计明确不在产品中保存收款资料，因此本次需要新增独立的数据、加密、访问审计与留存边界。保存资料本身不能完成自动转账；支付宝/微信自动转账还依赖运营主体的官方商户产品、证书、收款人标识、实名校验、限额和风控能力。

## Goals / Non-Goals

**Goals:**

- 只在官网首页底部展示合作伙伴活动入口，不改变工作台信息架构。
- 让运营人员从后台启停活动曝光和新用户加入，同时保留历史账务和对账能力。
- 安全保存人工结算所需的最小收款资料，并把每笔结算申请绑定到不可变的资料版本。
- 让运营人员按订单、账本、退款和结算状态完成可筛选、可审计的对账。
- 保持所有查询有界、分页并与面试、ASR、AI 回答、截图和支付热路径隔离。
- 为未来官方转账适配器预留稳定领域接口，但本期不宣称或执行自动打款。

**Non-Goals:**

- 接入支付宝或微信自动转账、代扣税、自动开票或自动实名校验。
- 收集身份证号、银行卡号、收款码图片、聊天记录或任何面试内容。
- 向普通合作伙伴展示被推广用户身份或逐用户行为。
- 修改佣金比例、30 天注册归因、90 天订单窗口、7 天观察期或每月一次结算规则。

## Decisions

### 1. 活动入口只属于官网首页底部

官网首页 Footer 之前使用独立的底部活动区承载合作伙伴计划，展示 20% 佣金要点和明确 CTA；登录后的桌面侧边栏和移动菜单都不展示合作伙伴入口。入口跳转到现有受保护的 `/app/partner-program`，未登录用户按现有登录边界处理，登录后可继续访问合作伙伴看板。

不使用弹窗、常驻动画或工作台活动卡片，避免干扰面试准备和低性能设备。

### 2. 活动开关采用数据库中的运行时配置

环境变量继续作为部署级总开关；新增数据库运行时开关作为运营控制面。后台拥有 `promotion.manage` 权限的管理员可在“推广中心 → 合作伙伴”启停活动。关闭只停止官网入口曝光与新用户加入，不删除或改写历史推广链接、归因、佣金、收款资料和结算记录，管理员仍可继续对账和人工结算。变更原因、操作者与配置版本进入审计。

### 3. 收款资料采用追加式版本而不是覆盖字段

新增 `partner_payout_profiles`，每次保存创建新版本并停用上一版本。记录支付方式、密文姓名、密文账号、脱敏展示值、版本、状态和时间，不把敏感字段放在合作伙伴主表。结算申请保存 `payout_profile_version_id`，因此用户后续换绑不会改变已提交申请。

替代方案是在 `partner_profiles` 上直接覆盖账号，结构更简单，但无法重现历史结算目标，也不利于审计和争议处理，因此不采用。

### 4. 敏感字段使用独立生产密钥加密

使用独立 `OFFERSTEADY_PARTNER_PAYOUT_ENCRYPTION_KEY` 进行认证加密，密钥只存在服务端环境；日志、异常、审计详情和 API 默认响应禁止包含明文。用户和后台列表只返回支付方式及脱敏值。保存接口不回显明文。

未来轮换通过 `key_version` 支持新写入使用新密钥、受控任务迁移旧密文。不得复用用户 JWT、数据库密码或客户端配置作为加密密钥。

### 5. 明文查看是按次授权的高风险操作

只有拥有 `promotion.payout.manage` 且近期完成 MFA 的管理员，才能针对单笔结算申请调用明文查看接口。接口返回 `Cache-Control: no-store`，每次成功或失败均记录操作者、申请、时间和结果；不提供批量导出，不把明文写入前端持久存储。

普通管理员继续可以查看聚合金额、订单状态、脱敏收款状态和结算状态，但看不到完整账号姓名。

### 6. 对账视图直接读取权威订单与追加账本

后台增加：

- KPI：符合条件订单数、观察中订单/金额、可结算订单/金额、已预留、已结算、退款冲正和负数结转。
- 订单佣金表：订单号、合作伙伴推广码、净实收、佣金、支付时间、可结算时间、退款金额、当前状态和关联结算申请。
- 结算申请表：周期、申请金额、收款方式/脱敏账号、状态、申请/审批/支付时间及支付参考号。

查询使用游标或上限分页、已有时间/状态索引和独立管理连接预算；不扫描面试内容，不在支付回调同步计算。管理员主动“同步已支付订单佣金”仍是有界幂等投影。

### 7. 为自动转账预留端口但不提前接渠道

领域层预留 `PayoutProvider` 接口及 provider reference 字段。只有后续取得企业支付宝/微信官方转账产品、证书与合规确认后，才新增具体适配器和独立 OpenSpec 变更。当前 `paid` 状态仍由管理员确认真实打款并录入非敏感支付参考号触发。

## Risks / Trade-offs

- [收款账号泄露] → 独立密钥、认证加密、默认脱敏、MFA、按次审计、禁止批量导出与日志明文。
- [姓名或账号录错导致打款失败] → 用户保存前二次确认，结算申请展示脱敏快照，管理员打款前按次核对；本期不承诺渠道实名校验。
- [用户修改资料造成历史申请漂移] → 申请绑定不可变资料版本，修改只影响后续申请。
- [后台订单查询增加数据库压力] → 分页、索引、查询超时和独立并发预算；不进入任何用户热路径。
- [用户误认为已经自动到账] → 页面明确“人工审核、月底联系/打款”，自动渠道未接入前不展示“自动结算”。
- [敏感资料留存过久] → 只对存在结算关系的合作伙伴保存，账号注销后停止使用；按财税/争议留存期加密保留，到期执行受控删除。

## Migration Plan

1. 在当前生产版本之上增加纯追加表、索引和可空结算资料版本引用，保持新收款资料功能开关关闭。
2. 生成并配置独立生产加密密钥，验证密钥不会出现在日志和客户端构建中。
3. 发布后端与管理后台，先验证旧结算记录、权限、分页和脱敏显示。
4. 在无活跃面试时发布 Web 侧边栏和用户收款资料表单，再开启功能开关。
5. 使用合成账号完成“保存 → 申请 → 管理员脱敏查看 → MFA 明文查看 → 审批 → 标记支付”闭环后删除合成资料。
6. 异常时关闭收款资料开关并回滚应用；新增加密资料、账本和审计记录保留，不执行破坏性删表。

## Open Questions

- 本次是否确认只上线“加密保存资料 + 人工审核打款”，把支付宝/微信官方自动转账作为取得商户能力后的下一期？
- 收款姓名应使用自然人真实姓名还是允许企业名称；首版建议仅支持自然人实名姓名。
- 财税或争议留存期由运营主体最终确认；实现先使用可配置期限且不做未经确认的自动删除。
