## Context

用户已批准仅修复回答启动和截图二次异常。国服运行镜像与本地全量源码不完全一致，不能直接整包部署本地 HEAD。计费正常分支从数据库行显式映射记录，但余额不足分支直接展开调用参数；截图安全包装器的内层异常日志缺少必需参数。

## Goals / Non-Goals

**Goals:** 恢复既有余额不足语义；截图异常路径不再产生参数 TypeError；保留脱敏根因；无活动面试时部署可回滚的最小后端补丁。

**Non-Goals:** 不改计费价格、会员门槛、AI 输出、音频、轮询、缓存、内存回收；不部署前端、Admin、国际服或桌面程序；不执行数据迁移。

## Decisions

1. 在仓储的余额不足返回分支显式构造 UsageReservationRecord 支持的字段。会员资格参数仅用于查询，不增加无意义的持久化字段，也不吞掉任意 TypeError。
2. 截图原始失败和恢复失败分别记录错误类别；调用现有日志方法时完整提供 task/image_count/retry_count。日志不包含异常原文、图片或机器码。继续保留既有失败状态和取消校验，不扩大截图生命周期改造。
   回归测试进一步发现：计费异常发生在 SSE 响应头发送后，修复字段后仍会转成连接异常。因此在现有专用执行器中预取第一个事件，再开始响应；这样启动阶段余额不足可返回现有 HTTP 409 错误壳，不增加一次计费调用，也不等待模型回答。该修正属于回答启动 Bug 的端到端修复，涉及第三个生产文件 `modules/live_answer.py`。
3. 用合成数据库游标覆盖真实 PostgreSQL 仓储分支，并增加隔离 PostgreSQL 集成测试；补充失败接口语义和截图异常恢复测试，先证明旧代码失败再验证修复。
4. 从运行镜像导出无凭证源码构造隔离候选，应用同一最小补丁。以运行镜像为父层，仅替换三个修复文件，避免其他本地改动上生产。

## Risks / Trade-offs

- [余额不足仍影响用户使用] → 这是正确业务限制，只恢复明确提示，不绕过计费。
- [截图底层错误仍存在] → 本次修复二次异常并保留原始错误；不宣称所有 OSS/模型失败均被消除。
- [部署撞上新面试] → 测试通过后核验数据库 live 数、容量活动及音频数；切换前再次即时复查，非零即停止切换并等待。
- [源码或镜像漂移] → 核验实际容器镜像 ID 和文件哈希；仅 backend no-deps 更新，记录其他容器 ID 不变。

## Migration Plan

本地回归与候选基线回归通过 → 保留旧镜像及配置定位 → 空闲门禁 → 仅切换 backend → 健康、鉴权和无新 TypeError 核查。失败则只回滚 backend 镜像。不改用户数据。
