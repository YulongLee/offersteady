## Context

认证和计费依赖当前使用共享的 `_fallback_to_memory_repository`：开发环境中PostgreSQL连接失败会退回内存实现。该机制适合早期原型，但对积分账务会造成两个连锁问题：认证内存重置可能生成新 `user_id`，计费内存重置则丢失流水并重新执行新用户赠送。生产环境已经禁止降级，但本地与预发布若错误使用开发模式仍可能制造看似“积分自动充值或重置”的数据。

## Goals / Non-Goals

**Goals:**

- 配置数据库时让认证和计费故障关闭，不再退回内存。
- 保证手机号身份、积分余额和赠送流水跨服务重启稳定。
- 保留测试直接构造内存仓库的能力。
- 不改变一次性200点赠送和现有积分费率。

**Non-Goals:**

- 不修改商品价格、会员、支付或兑换码规则。
- 不自动删除或改写现有积分流水。
- 不在本轮增加运营管理后台。

## Decisions

### 1. 认证和计费使用故障关闭

当 `database_url` 存在时，仓库工厂直接构造PostgreSQL实现；连接失败向上抛出，由服务健康检查和API错误处理暴露故障。只有未配置数据库或测试直接构造服务时才允许内存实现。

替代方案是增加自动重试后继续回退内存。该方案提高页面可用性，却会破坏账户和账务一致性，因此不采用。

### 2. 保留数据库幂等赠送

`welcome:<user_id>` 继续作为唯一账本引用，使用 `INSERT ... ON CONFLICT DO NOTHING`。赠送检查可以保持惰性触发，因为数据库约束能够处理重复页面读取、并发与重启。

替代方案是把赠送移动到短信注册事务。认证和计费当前是独立模块，跨域事务会增加耦合；现有唯一账本约束已经提供所需的一次性语义。

### 3. 不自动清理现有数据

修复只阻止未来的内存降级。线上账本是否存在异常需要通过只读查询审计，未经确认不执行余额修正。

## Risks / Trade-offs

- [数据库短暂不可用时积分页面不可用] → 明确返回服务异常并由容器健康检查恢复，优先保证账务正确性。
- [本地开发未启动PostgreSQL时后端相关模块失败] → 使用项目Docker PostgreSQL；纯单元测试继续直接构造内存服务。
- [已有重复用户身份] → 本修复阻止新增，历史账号合并需单独审计和人工确认。

## Migration Plan

1. 部署故障关闭的仓库装配逻辑和回归测试。
2. 确认生产环境 `OFFERSTEADY_ENV=production` 和PostgreSQL数据卷存在。
3. 重建后端并执行健康检查与积分状态检查。
4. 观察数据库连接错误和账本异常日志；不自动调整历史余额。
5. 如需回滚，仅回滚应用代码，不删除数据库卷。
