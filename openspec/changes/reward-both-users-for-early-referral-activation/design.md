## Context

现有邀请功能为每个用户生成稳定分享链接，每个被邀请账号终身最多激活一次，并在 PostgreSQL 事务中只向分享者写入 `referral_credit` 流水。当前增长配置只有启用状态和单次分享者奖励，用户端没有注册窗口资格或新用户奖励信息。

本变更横跨认证注册时间、邀请事务、积分账本、后台增长配置和 Web 状态展示。时间与积分都必须由服务端判定，且不得破坏已有邀请关系和已发放流水。

## Goals / Non-Goals

**Goals:**

- 只允许注册后 72 小时内的新账号首次激活邀请链接。
- 一次成功激活同时奖励分享者和新用户，保证关系与两笔积分原子、幂等。
- 后台分别控制两类奖励，用户端清楚看到资格截止时间和双方收益。
- 保留现有自邀禁止、终身一次、活动开关、稳定链接和隐私边界。

**Non-Goals:**

- 不补发本变更上线前已经激活的用户，也不撤销历史积分。
- 不实现多级邀请、现金返佣、排行榜或设备/IP 指纹风控。
- 不由客户端计算最终资格、奖励金额或直接修改积分余额。

## Decisions

### 1. 资格窗口使用账号服务端注册时间和服务端当前时间

激活服务以认证用户持久化的 `created_at_ms` 为起点，使用请求到达服务端时的时钟判定 `now_ms <= created_at_ms + 72h`。邀请状态接口返回 `eligibleToActivate`、`activationDeadlineMs` 和稳定原因码，Web 只负责展示。

替代方案是首次登录或首次打开邀请页开始计时，但它可被重复会话影响，也无法稳定审计，因此不采用。客户端倒计时只用于体验，不作为授权依据。

### 2. 双方奖励使用两条可区分且唯一的账本流水

保留现有分享者 `referral_credit` 流水，新用户使用独立的 `referral_invitee_credit` 类型；两条流水分别以激活 ID 和角色构造唯一引用。邀请激活事务按稳定顺序锁定两个账号，插入关系和双方流水后一次提交。

替代方案是复用同一个不区分角色的流水类型，会使后台统计和用户明细含义不清；先后分两次事务入账会产生一方到账、另一方失败，因此不采用。

### 3. 配置分别保存两项奖励，并在激活记录中快照

增长配置增加 `inviter_reward_points` 与 `invitee_reward_points`，合法范围均为 1–100000。现有 `reward_points` 数据迁移为分享者奖励，新用户奖励初始化为 500；激活记录同时保存两项额度、配置版本和资格截止时间。

分别配置比强制双方同额更适合后续运营，但默认都为 500 点以符合当前产品展示。历史记录永远读取快照，不受配置变更影响。

### 4. 三天窗口作为当前固定产品规则展示

本轮数据库和 API 使用固定 72 小时常量，后台展示规则但不开放修改，避免运营误配导致用户承诺频繁变化。若后续验证需要调整，再通过带版本和审计的独立配置字段扩展。

这比立即提供可变天数更符合当前明确需求，也减少边界测试和历史解释复杂度。

### 5. 兼容历史数据与旧客户端

迁移为新配置字段提供默认值，不改历史激活记录和 `referral_credit`。API 保留已有分享者 `rewardPoints` 字段作为兼容别名，同时增加明确的 `inviterRewardPoints`、`inviteeRewardPoints` 和资格字段。旧 Web 仍可读取分享者奖励，新 Web 使用新字段。

## Risks / Trade-offs

- [批量注册刷双方积分的收益提高] → 保留一次性、自邀禁止和后台总开关；记录双方用户与激活时间，后续可增加注册速率和设备/IP 风控。
- [服务器时间或旧账号时间数据异常] → 统一 UTC 毫秒并以数据库事实为准；缺失注册时间的旧账号默认不可激活而不是放宽权限。
- [部署中旧代码不认识新账本类型] → 先部署兼容数据库约束和后端，再部署 Admin/Web；所有账本初始化器都必须包含新类型。
- [双用户锁导致死锁] → 按排序后的用户 ID 获取锁，并将外部调用排除在事务之外。
- [用户在页面停留到过期边界] → Web 倒计时到期立即禁用，但后端仍做最终判定并返回稳定过期结果。

## Migration Plan

1. 新增配置字段、激活快照字段和 `referral_invitee_credit` 账本约束，使用向后兼容默认值。
2. 部署支持旧/新字段的后端，并验证历史邀请状态、余额和流水不变。
3. 部署 Admin 双奖励配置与 Web 资格/双方奖励展示。
4. 使用合成账号验证 72 小时前、边界时刻、边界后、并发重试、自邀、活动关闭和任一流水失败回滚。
5. 回滚 Web/Admin 时保留新字段；回滚后端前停止新激活，避免旧后端读取不了新账本类型。

## Open Questions

- 当前建议默认分享者与新用户各 500 点，并允许后台分别调整；如运营需要强制同额，可在实施前将后台收敛为单一奖励配置。
