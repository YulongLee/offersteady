## Context

会员权益目前分存在 `billing_time_pass_entitlements` 和 `admin_time_entitlements`。读取状态时会合并两张表，但付费到账只查询前一张表的最晚到期时间，因此后台权益仍有效时，新购买权益会从支付时间开始并与其重叠。后台调整虽然会查询两张表，却没有和支付到账使用相同的用户级事务锁。

## Goals / Non-Goals

**Goals:**

- 所有会员来源共享同一条“接在最晚到期时间之后”的规则。
- 同一用户并发获得付费和后台权益时不会产生重叠。
- 重复支付通知保持幂等。
- 修复已确认的单笔受影响权益，并核验最终到期时间。

**Non-Goals:**

- 不改变商品价格、会员天数或支付渠道。
- 不合并或删除历史订单。
- 不改变积分结算和知识材料额度规则。

## Decisions

1. 付费到账事务在现有用户级 advisory lock 内分别读取付费权益与后台权益的最大 `ends_at_ms`，再以支付时间和两个最大值的最大者作为新权益起点。相比新增汇总表，这个改动更小，也不需要迁移现有数据模型。
2. 查询后台权益前使用 `to_regclass` 判断表是否存在，兼容未启用商业后台的测试或旧环境；不存在时仅使用付费权益结果。
3. 后台会员调整获取与支付到账相同的用户级 advisory lock，避免两个来源并发发放时都读到相同旧到期时间。
4. 服务端返回的权益段保持真实；当当前段与待生效段形成连续时间线时，顶部权益卡展示累计剩余时间和最终到期时间，下方仍保留待生效段明细。
5. 已受影响订单通过部署后的单次事务修复：锁定目标用户，将该付费权益移动到原后台权益结束之后，保持购买天数不变。修复前后均查询并记录结果。

## Risks / Trade-offs

- [后台权益表不存在] → 使用 `to_regclass` 降级，避免支付确认失败。
- [支付与后台调整并发] → 两条写路径使用同一个用户级 advisory lock。
- [数据修复目标错误] → 只操作已核对订单号，事务内校验订单已支付、商品为 1 天会员且权益仍重叠；条件不满足则不更新。
- [重复通知重复延长] → 保留订单状态检查与 `ON CONFLICT (order_id) DO NOTHING` 幂等约束。
