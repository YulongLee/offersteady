## Context

OfferSteady 当前以 React/Vite 用户端、FastAPI 后端、PostgreSQL/pgvector、Redis、OSS 和 Docker/Nginx 提供服务。用户、订单、积分/时长账本、资料任务和面试会话已有持久化基础，但运营处理主要依赖服务器和数据库操作，缺少权限隔离、审计和安全操作入口。

后台涉及财务、账号和用户隐私，不能把普通用户登录直接升级为管理入口，也不能为了后台重构当前用户端。设计需要支持低风险灰度、快速关闭以及后续从单体后端拆分服务。

## Goals / Non-Goals

**Goals:**

- 在不改变用户端原型和公开 API 契约的情况下提供独立商业后台。
- 对后台访问实施显式管理员授权、MFA、最小权限 RBAC、短会话和撤销。
- 对财务、账号、资料和面试操作提供幂等、可审计的安全命令。
- 提供脱敏的业务与技术可观测性，减少直接访问数据库和服务器。
- 支持默认关闭、独立灰度和无影响回滚。

**Non-Goals:**

- 不在首版提供退款、营销自动化、客服工单、CMS 或复杂 BI。
- 不允许后台直接修改数据库、覆盖账本、编辑 OSS 或任意标记订单已支付。
- 不默认展示简历、JD、知识库、音频、截图和模型提示词原文。
- 不改变用户端页面、登录、支付、资料、面试和桌面助手现有行为。
- 不在首版拆分独立管理微服务。

## Decisions

### 1. 独立后台前端与隔离 API

新增独立后台前端应用，生产建议使用 `admin.mianshiwen.cn`，后端接口统一位于 `/api/v1/admin/*`。后台构建物不进入现有用户端路由和主包。

选择该方案是为了实现独立发布、CSP/CORS、访问控制和回滚。将后台页面加入现有用户端被否决，因为容易产生路由暴露、包体增长和权限误用。

### 2. 同一 FastAPI 进程中的独立管理模块

首版在现有 FastAPI 中增加独立 router、依赖、service、repository 和 schema，复用已有领域服务与事务边界，不直接复用用户 API handler。

选择该方案是为了降低当前服务器资源和部署复杂度，同时保持未来可抽离边界。立即新增管理微服务被否决，因为会引入额外服务发现、鉴权和一致性成本。

### 3. 显式管理员授权和 MFA

管理员身份通过独立授权记录关联真实用户 ID，并包含角色、状态和授权版本。普通用户 JWT、手机号或用户名 `admin` 均不足以访问后台。登录先验证现有账号身份，再完成 TOTP MFA，签发短时管理会话；高风险动作要求近期 MFA 证明。

首位 `super_admin` 只能通过服务器侧 CLI 引导创建，公共接口不能授予该角色。相比复用用户 token 或配置固定密码，该方案更可撤销、更可审计且不在客户端保存管理密钥。

### 4. 拒绝优先的 RBAC

权限按动作定义，例如 `users.read`、`users.suspend`、`billing.read`、`billing.adjust`、`payments.reconcile`、`materials.retry`、`sessions.terminate`、`observability.read` 和 `admins.manage`。角色只映射权限集合，未明确允许即拒绝。

预置角色为 `super_admin`、`operations`、`support`、`finance` 和 `technical_auditor`。首版不提供浏览器内自定义权限编辑，避免误配置。

### 5. 命令式安全操作

后台写操作调用领域命令而不是直接更新表：

- 积分/时长调整追加账本流水，余额由权威账本计算。
- 支付仅触发已有对账流程，不提供“设为已支付”。
- 资料仅重试失败任务，不直接编辑状态或 OSS。
- 结束面试调用现有会话终止逻辑并释放活跃绑定。
- 封禁账号同时提升授权版本并撤销用户会话。

每个命令携带原因、幂等键、管理员身份和请求 ID，并在同一事务或可恢复工作流中写入审计结果。

### 6. 追加式脱敏审计

`admin_audit_events` 只追加，不提供后台修改和删除接口。记录操作者、角色、动作、资源类型与 ID、安全前后摘要、原因、请求 ID、来源 IP/设备摘要、结果和时间。敏感字段统一通过 allowlist 序列化，禁止记录正文、凭证和模型密钥。

只依赖应用日志被否决，因为日志轮转、结构变化和跨请求关联不足以支持财务与安全审计。

### 7. 只读聚合与隐私最小化

运营列表默认分页、脱敏并限制时间范围。用户手机号仅显示掩码；资料只显示文件名、安全状态、处理阶段和时间；AI/RAG 与实时链路只显示计数、延迟、错误码和追踪 ID。敏感详情需要独立权限，首版不开放原文。

### 8. 默认关闭和渐进启用

使用 `OFFERSTEADY_ADMIN_ENABLED=false` 作为总开关，并单独配置管理来源、会话期限和 MFA。关闭时管理页面不可达，管理 API 返回不可发现结果，用户 API 不经过管理依赖。

数据库迁移为纯增量。发布顺序为：迁移 → 后端关闭状态部署 → 创建首位管理员 → 部署管理前端 → 配置管理域名 → 小范围开启。回滚只需关闭入口和 API，保留审计数据。

## Risks / Trade-offs

- [同一后端进程仍共享故障域] → 管理查询设置独立限流、超时和数据库连接预算，禁止大范围无分页扫描；后续达到负载阈值再拆分。
- [管理员账号被接管] → MFA、短会话、会话撤销、近期验证、最小权限和登录限流。
- [高风险动作误操作] → 二次确认、必填原因、幂等键、领域约束和完整审计。
- [后台查询泄露用户隐私] → 字段 allowlist、默认脱敏、禁止原文、导出功能不纳入首版。
- [灰度配置错误影响用户端] → 默认关闭、独立域名和 router、用户端回归测试、可单独回滚。
- [聚合查询增加数据库压力] → 分页、索引、短时缓存、时间窗和慢查询指标。

## Migration Plan

1. 添加增量表和索引，保持功能关闭。
2. 实现管理鉴权、RBAC、审计和只读 API，并完成安全回归。
3. 实现独立后台前端和只读运营页面。
4. 实现受控写操作及幂等、事务和审计测试。
5. 通过服务器 CLI 创建首位 `super_admin` 并绑定 MFA。
6. 部署独立管理域名，仅允许明确来源，先向单一管理员灰度。
7. 观察错误率、查询延迟和审计完整性后再开放其他角色。
8. 回滚时关闭总开关和管理域名，不回退增量表，不影响用户服务。

## Open Questions

- 正式管理域名是否使用 `admin.mianshiwen.cn`，上线前由用户确认 DNS 与证书。
- 首位超级管理员绑定的手机号和 TOTP 设备在 apply 阶段通过线下引导确定，不写入仓库。
- 自动退款和客服查看敏感内容继续保持关闭，待支付资质与隐私流程确认后另立 OpenSpec。
