## Context

当前桌面端已经拥有稳定 `deviceId` 和机器码，后端也保存实时 session binding，但网页和助手把“系统权限”“设备是否属于当前账号”“本场是否建立实时 lease”压缩成一个 `bound` 状态。新建 session 或恢复历史 session 时，这个状态容易回到 false，UI 随即把它解释成助手未授权，原生采集也不会启动。

macOS 权限由 TCC 按应用代码身份管理，网页无法也不应代替桌面应用授权。商业产品需要稳定签名才能保证升级后权限身份稳定；当前 ad-hoc 开发包只能保证同一构建身份内复用授权。

## Goals / Non-Goals

**Goals:**

- 将系统权限、账号设备绑定和面试连接拆成三个独立状态。
- 持久保存账号最近成功使用的设备，新面试结束不解除绑定。
- 新面试支持机器码连接，历史面试支持复用最近设备或重新输入。
- 同一用户和设备同时只保留一个活动实时 lease，并允许新面试明确接管旧 lease。
- 网页只显示桌面权限诊断，不触发浏览器麦克风或屏幕权限。

**Non-Goals:**

- 不绕过 macOS 首次权限确认，不伪造系统授权结果。
- 不改变音频、截图和转录的默认数据保留策略。
- 不重做准备页和实时页视觉结构。
- 不在本变更内完成 Developer ID 申请、公证或 Windows 客户端。

## Decisions

### 1. 三层状态分别建模

桌面报告 `permissions` 和 `presence`；账号设备关系保存为 durable association；本场连接保存为带 TTL 的 session lease。API 响应必须分别返回这些字段，`bound=false` 只表示当前 session 未连接，不能映射为系统权限缺失。

替代方案是继续扩展单一 `bound` 枚举。该方案无法表达“已授权、设备在线、当前面试未连接”，因此拒绝。

### 2. 最近设备属于账号而不是面试

每次机器码连接成功后更新账号的 `last_device_id`。结束或创建面试只撤销 session lease，不删除账号设备关系。历史面试的一键连接从账号最近设备建立新 lease，并校验设备仍在线、仍属于当前账号。

替代方案是从历史 session 推断设备。历史 session 可能过期或被清理，不能作为长期设备关系事实源。

### 3. 新面试和历史面试使用不同默认动作

新面试默认展示机器码输入，保持用户对当前采集设备的明确选择。历史面试默认提供“一键连接上次设备”，同时保留“重新输入机器码”。两条路径最终调用同一个幂等的 lease 建立服务。

### 4. 新 lease 原子接管旧 lease

同一账号或设备建立新 lease 时，后端原子关闭旧活动 lease，再创建或恢复目标 session lease。旧网页显示已被其他面试接管，不能继续消费新音频。

### 5. 权限只由助手触发

助手首次调用麦克风、ScreenCaptureKit 或截图能力时触发 macOS TCC。网页只读取助手报告的 `granted/denied/not-determined` 状态并提供操作说明，不调用浏览器媒体权限 API。

## Risks / Trade-offs

- [ad-hoc 构建升级后 macOS 可能重新识别代码身份] -> 开发版明确提示，正式版使用固定 Developer ID 签名和公证。
- [最近设备离线] -> 一键连接返回可恢复错误并直接展示机器码输入，不误报权限问题。
- [多标签页竞争] -> 由后端 lease version 和 owner session 决定权威连接，旧页面只读展示被接管状态。
- [旧数据没有账号设备关系] -> 首次成功输入机器码时自动回填，不批量猜测历史归属。

## Migration Plan

1. 增加账号设备关系和最近设备访问接口，兼容现有注册记录。
2. 将现有 session binding 写入新 lease 服务并保留兼容响应字段。
3. 更新准备页的新建/历史连接入口和状态文案。
4. 更新助手状态映射，系统权限与面试连接分别显示。
5. 运行后端、Web、桌面测试及端到端合成连接测试。
6. 先部署兼容后端，再部署 Web，最后发布新助手。

回滚时保留新增设备关系数据，Web 可回退旧入口；后端兼容字段在至少一个版本周期内不删除。
