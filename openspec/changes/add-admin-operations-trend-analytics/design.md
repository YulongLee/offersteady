## Context

管理后台当前通过 `AdminRepository.dashboard()` 即时聚合生产业务表，适合展示当前状态，但结果不会按日期保存，也无法回答“最近 30 天用户和面试是否增长”“支付成功率是否下降”等运营问题。随着业务表增长，每次为曲线扫描原始表还会增加数据库压力。

本变更只扩展独立管理后台和 `/api/v1/admin/*` 接口，不改变用户端、桌面助手、积分扣费、支付、面试和资料处理的现有行为。统计只处理脱敏聚合值，不持久化音频、截图、资料正文或对话内容。

## Goals / Non-Goals

**Goals:**

- 永久保存自然日运营快照，并保留近期小时级快照用于故障分析。
- 提供口径稳定的 7/30/90 天趋势、区间汇总和环比。
- 覆盖增长、使用、收入、资料处理和系统质量五类核心指标。
- 聚合失败、回填或后台图表异常不得影响用户端主链路。
- 支持幂等回填、重跑、权限校验和数据更新时间说明。

**Non-Goals:**

- 不建设任意 SQL、拖拽式 BI、自定义指标或用户行为画像平台。
- 不将手机号、用户 ID、资料、对话、截图或模型输入输出写入快照。
- 不承诺回填部署前未持久化的实时延迟与错误指标。
- 不更改现有管理后台视觉语言和用户端产品原型。

## Decisions

### 1. 使用独立聚合快照表，而不是每次查询原始业务表

新增 `admin_metric_snapshots`，核心字段为 `bucket_start_at`、`granularity`、`metric_key`、`metric_value`、`sample_count`、`coverage_state`、`computed_at`。通过 `(bucket_start_at, granularity, metric_key)` 唯一约束实现幂等更新；指标名使用服务端 allowlist，首版不开放任意维度。

选择快照表是为了固定统计口径、降低查询成本并支持历史保留。替代方案是前端请求时扫描业务表，开发更少但会随数据增长变慢，历史业务结构变化也可能让旧日期结果漂移，因此不采用。

### 2. 日快照永久保留，小时快照保留 180 天

自然日以 `Asia/Shanghai` 切分，数据库时间统一使用 UTC。日快照作为长期运营事实永久保留；小时快照用于近期故障定位，默认保留 180 天，避免无限增长。

用户要求的“历史天数数据一直保存”由日快照满足。完全永久保存小时数据会带来不必要的存储和索引成本，因此不采用。

### 3. 使用幂等聚合命令和 PostgreSQL advisory lock

新增可独立运行的聚合命令，生产按小时执行，并在跨日后补算前一自然日。命令使用 PostgreSQL advisory lock 保证多实例只有一个执行者，使用 upsert 保证重试不会重复累计。部署阶段可指定日期范围回填历史数据。

相比把定时逻辑绑定某个 Web 进程，独立命令更容易监控和重跑；相比引入 Celery 等新基础设施，复用 PostgreSQL 更符合当前项目规模。

### 4. 区分可回填指标和部署后指标

注册、面试、账本、订单和资料任务等已有持久化时间字段的指标可回填。历史 ASR/模型首字延迟、错误率若没有完整持久化事件，只从本能力上线后的 `coverage_start` 开始统计。接口必须返回覆盖状态，图表不得把缺失值绘制为零。

这避免为了曲线“好看”而伪造历史数据。

### 5. 固定首版指标目录

首版指标包括：

- 增长：新增用户、活跃用户。
- 面试：创建面试、完成面试、有效活跃面试、回答次数、截图回答次数。
- 商业：积分消耗、创建订单、支付成功订单、支付成功金额、支付成功率。
- 资料：上传数量、处理成功数量、处理失败数量、处理成功率。
- 质量：AI 请求量、AI 错误率、回答首字延迟、ASR 最终转写延迟、实时链路错误数。

所有指标在一个服务端注册表中定义名称、单位、聚合方式、可回填性和说明，避免前后端各自解释。

### 6. 趋势 API 返回适合图表的稳定契约

新增 `GET /api/v1/admin/analytics/trends?range=7d|30d|90d&metrics=...`。响应包含时区、起止时间、生成时间、指标元数据、按日期对齐的数据点、区间汇总、上一等长区间对比和覆盖状态。只允许 `observability.read` 管理权限，限制范围和指标数量。

即时总览卡继续使用现有接口，趋势接口读取快照，避免历史与瞬时口径混在一起。

### 7. 管理端使用轻量 SVG 曲线

在现有运营总览下增加时间范围切换、五类分析卡和 SVG 折线/面积图，复用现有 CSS 变量和页面结构。首版不引入大型图表依赖，降低管理端包体和供应链风险；图表提供图例、单位、空数据、加载失败和更新时间状态。

## Risks / Trade-offs

- [历史数据字段不完整] → 标记 `partial` 或 `from-deployment`，不以零值代替缺失。
- [统计口径后续调整] → 指标注册表保留版本，已落盘快照记录口径版本，变更时显式回填。
- [聚合查询影响生产库] → 按时间索引增量扫描、限制回填批次、低峰执行，并用 advisory lock 防止并发。
- [时区边界造成重复或漏算] → 所有 bucket 转换集中在服务端，测试夏令时无关的上海自然日边界。
- [图表指标过多难以阅读] → 默认只展示核心指标，按五类分组，不允许用户任意叠加无限曲线。
- [调度中断造成日期缺口] → 每次执行自动检查最近缺口并幂等补算，后台显示最后成功聚合时间。

## Migration Plan

1. 增量创建快照表、执行记录表和索引，不修改现有业务表。
2. 部署后端趋势接口与聚合命令，但管理端暂不展示入口。
3. 在低峰期回填可可靠推导的历史日数据，记录每项指标覆盖范围。
4. 核对指定日期的快照与原始表抽样结果，并运行查询性能检查。
5. 部署管理端曲线，默认查询 30 天；聚合异常时保留现有即时总览。
6. 配置小时调度并监控最近成功时间和缺口数。

回滚时隐藏管理端趋势区域并停止调度，保留快照表；用户端及现有运营功能不受影响。

## Open Questions

- 首次上线回填范围默认取现有业务表可用的全部历史日期；若数据量超出单次低峰窗口，则分批完成。
- 小时快照 180 天保留期后续可根据实际数据库体积调整，日快照仍永久保留。
