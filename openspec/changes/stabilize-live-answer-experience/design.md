## Context

实时工作台接收快答/手动输入、网页截屏和助手快捷键截屏三类显式回答来源；语音识别只提供转写和问题候选。当前页面把本地占位任务、流式回调、1.5 秒历史快照和截屏轮询分别合并；它们没有共享严格的任务新旧判断，较旧快照或迟到回调可能覆盖正在生成的新任务。流式正文又在每个小分片到达时直接重渲染和重新拆分“简单/详细回答”，造成文字跳动、占位内容闪现。快答和截屏回答虽可点击，但缺少统一的处理中、完成和失败反馈。

本次变更涉及 Web 状态归并、组件交互和可能的后端自动确认门槛，必须保持现有语音说话人分流、计费、资料选择和模型适配器不变。测试只能使用合成问题、合成答案及合成截图元数据，不记录完整真实问题或回答。

## Goals / Non-Goals

**Goals:**

- 新回答任务开始后立即显示对应问题，旧快照和迟到事件不能把页面切回旧问题。
- 流式内容单调增长并按可感知的短时间窗口批量呈现，降低逐字抖动和布局闪烁。
- 快答与截屏回答具有明确、可访问、可防重复提交的操作状态。
- 任何语音问题都不自动生成答案；只有快答和截屏回答能显式触发模型调用。
- 用纯状态归并测试、组件测试、前后端回归和生产构建覆盖关键竞态。

**Non-Goals:**

- 不调整说话人声道映射、语音供应商、模型供应商、Prompt、资料检索或积分费率。
- 不引入 WebSocket、新数据库表或新的持久化内容。
- 不改变历史答案分页的产品能力，也不强制打断用户主动查看历史答案。
- 不修改桌面助手采集和发布包，除非验证证明问题来自助手协议；当前设计不预期需要修改。

## Decisions

### 1. 用确定性的任务优先级归并所有回答更新

Web 端增加一个可单元测试的归并函数，以 `questionId/taskId` 识别任务，以 `revision`、`updatedAtMs` 和状态阶段判断同一任务的新旧。新任务只在时间更新或由当前用户显式发起时取得“当前任务”所有权；同一任务的状态只能从 queued/generating 向 completed/failed/cancelled 单调推进。较旧历史快照可补充历史列表，但不得覆盖更新的活动任务或已增长的正文。

显式的快答、手动回答和截屏回答会立即创建本地占位任务并切回最新答案。语音转写和问题候选更新不会改变当前答案；历史答案仍可通过导航查看。

选择该方式是因为现有接口已经携带任务 ID、revision 和更新时间，可以在不改数据模型的前提下消除竞态。替代方案是让后端返回全局序列号或改成单一长连接；这会扩大协议和部署范围，不适合本轮缺陷修复。

### 2. 将网络流与可视渲染解耦

流式回调仍立即接收并保存最新完整前缀，但 UI 以约 80–120 毫秒的短窗口或动画帧批量提交可视文本。归并函数拒绝长度缩短或非前缀的旧分片；已有正文不再被“正在整理”占位文案替换。简单回答出现后保持稳定，详细回答只有在任务仍进行中时显示补充提示，任务结束且无详细段时不继续宣称正在生成。

问题规范化状态继续作为内部任务元数据参与归并，但回答区不展示“正在整理面试官的问题”“AI 整理的问题”或 fallback 标签，避免状态切换时插入一行内容并推动问题标题与答案正文位移。问题正文和真实任务状态仍正常展示。

回答正文组件按正文内容缓存，实时收音、心跳和设备状态等无关更新不得重新解析相同答案。生成阶段使用保持 DOM 结构稳定的纯文本容器渐进更新；任务完成后再切换为完整 Markdown/代码/公式渲染，避免未闭合 Markdown 在每个分片到达时改变元素树。

选择小窗口批量渲染是因为它保留实时感和停止能力，同时显著减少 Markdown 解析与布局重排。替代方案是修改模型分片大小；这依赖供应商且不能解决快照覆盖和迟到事件。

### 3. 操作反馈与按钮职责分离

快答与截屏回答继续使用原生 `button`，并使用清晰的主要/次要按钮外观和至少 44px 的点击高度。截屏回答按钮始终展示固定的操作名称与说明，不把捕获、上传、识别、生成或完成状态替换进按钮文案；请求开始后只通过禁用同一操作防止重复。处理中反馈由回答区或现有处理弹窗承载，完成、失败或取消可通过独立的 `aria-live` 状态区反馈。快答在输入框为空时仍可使用最近的完整面试官问题，只有两者都不存在才阻止提交并说明原因。

选择固定按钮文案，是因为按钮负责表达可执行动作，变化的内部阶段会让用户误以为操作入口已经变成状态卡片。独立进度区域既能保持操作语义稳定，也能继续提供可访问反馈；不使用短暂 Toast，因为它容易消失且不能表达持续中的阶段。

### 4. 回答模型只接受用户显式触发

沿用后端现有说话人和候选问题流程，系统声道的 final 内容可以形成问题候选，但候选确认不创建回答任务。快答由用户点击后读取手动输入或最近可用的面试官问题；截屏回答由用户点击后进入独立截图链路。两种显式操作继续使用幂等键与处理中禁用状态防止重复调用和重复计费。

选择严格的人工触发边界，是为了避免连续转写把陈述句、追问片段或候选人自己的发言误当成新问题并生成答案，同时让用户明确控制模型调用和积分消费。

## Risks / Trade-offs

- [批量渲染增加极短延迟] → 将窗口控制在约 80–120 毫秒，并在 completed/failed/cancelled 时立即刷新最终内容。
- [客户端时间可能不完全可靠] → 同一任务优先使用 revision 和状态阶段；时间只用于不同任务排序，并让用户显式操作拥有当前任务优先权。
- [用户可能忘记点击快答] → 保持最近面试官问题可直接用于快答，并在按钮区提供清晰可用状态。
- [历史自动回答事件仍可能存在] → 只将其作为既有历史兼容数据读取，新转写不再创建此类事件。
- [主动查看历史时错过新答案] → 不强制跳转，但保持醒目的“有新答案 · 回到最新”入口。
- [Web/Backend 同时部署导致短暂版本差异] → 保持协议向后兼容，先部署 Backend（若有变更）再部署 Web；任何一侧均可独立回滚到上一镜像。

## Migration Plan

1. 先落地纯归并函数和回归测试，再替换工作台内分散的覆盖逻辑。
2. 调整回答渲染节奏与按钮反馈，运行 Web 单测、类型检查和生产构建。
3. 修改后端问题候选处理，使自动确认和人工确认都不创建回答任务，并运行对应 Python 回归测试；不做数据库迁移。
4. 提交并推送 Git，部署受影响的 Backend/Web 服务，不重启 PostgreSQL、Redis 或无关服务。
5. 用合成面试会话验证未点击时不回答、快答、截屏、历史切换、停止与失败恢复；检查健康接口和线上静态资源。
6. 若出现回归，回滚受影响服务到部署前镜像/提交；由于无数据迁移，回滚不需要数据处理。

## Open Questions

- 无阻塞问题。实现阶段以现有后端可信度与完整性字段为准；若字段不足，优先补充派生判断和测试，不新增供应商耦合。
