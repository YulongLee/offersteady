## Context

后台已经从支付渠道接口获得 `enabled`、`validationStatus`、`validationErrors`、`configVersion`、`updatedAtMs` 和敏感字段掩码状态，但当前卡片只用普通文本和一个“开启/关闭渠道”按钮呈现。保存成功提示强调加密，却没有直接回答该支付方式是否出现在用户端；同时支付卡片局部捕获 `admin_session_invalid` 后只显示内部错误码，不会像页面加载失败那样恢复登录流程。

## Goals / Non-Goals

**Goals:**

- 让管理员无需推断即可判断渠道是否正在对用户开放。
- 以明确开关控制现有渠道激活接口，并在不可开启时解释原因。
- 将配置完整性和用户端生效状态分开呈现。
- 支付设置操作遇到失效会话或近期 MFA 过期时进入统一、可恢复的重新登录流程。

**Non-Goals:**

- 不新增支付渠道字段、数据库列或后端路由。
- 不进行真实商户连通性探测，也不把静态 `ready` 描述成真实支付验收通过。
- 不改变保存配置后自动关闭渠道、历史订单继续处理回调或权益幂等规则。

## Decisions

### 1. 从既有服务端字段派生两类状态

卡片将 `enabled && validationStatus === "ready"` 显示为“用户端正在使用”，否则显示“用户端未使用”；配置状态单独显示为“配置可启用”或“配置待完善”。这样不引入重复状态源，用户端可用性仍由后端决定。

替代方案是新增“是否使用”数据库字段。现有 `enabled` 已是权威开关，重复字段会产生不一致，因此不采用。

### 2. 使用可访问的开关控件调用现有激活接口

每个渠道使用带文本标签的 checkbox switch。配置非 `ready` 时开关禁用，并就地展示校验错误；切换前继续要求变更原因和确认。操作成功后重新读取服务端数据，不乐观伪造状态。

替代方案是保留普通按钮并增加颜色。按钮仍难以表达持续状态，不能解决当前误解。

### 3. 明确区分静态校验与真实支付验收

`ready` 只表示字段齐全且本地格式可解析，界面使用“配置可启用”，不使用“支付已验证”。已开启状态说明“用户支付页可选择”，并提示仍需完成真实小额订单验收。

### 4. 统一处理管理员鉴权错误

API 层识别 401 和 `admin_session_invalid`，清理 sessionStorage 并抛出可识别的会话错误；App 向支付面板提供统一的重新登录处理。`admin_step_up_required` 同样引导重新验证，避免在密钥表单下方暴露内部错误码。

替代方案是仅延长会话时间。延长高风险后台会话会降低安全性，且不能修复失效后页面状态不一致。

## Risks / Trade-offs

- [管理员把“配置可启用”误认作真实支付已验收] → 状态说明明确标注仅完成格式校验，并保留小额支付验收提示。
- [切换开关时网络失败] → 不做乐观更新，失败后保留服务端原状态并显示可读错误。
- [会话失效导致未提交密钥丢失] → 页面在提交失败时说明需重新登录；出于安全边界不把私钥草稿持久化到本地。
- [视觉改动影响商品卡片] → 使用支付卡片专用类名，不复用商品发布开关样式。

## Migration Plan

1. 部署 Admin 静态资源，不变更 Backend、数据库或 Web 用户端。
2. 使用当前线上 `draft/disabled` 微信配置确认显示为“用户端未使用、配置待完善”。
3. 使用合成 ready/enabled 状态运行前端测试，确认开关和说明正确。
4. 回滚时恢复上一版 Admin 静态资源；服务端支付状态不受影响。
