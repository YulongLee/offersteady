## Context

设备页目前直接读取 `state.preparation.device`，固定渲染“在线”“权限正常”，并且“诊断”按钮没有事件，因此它不是账号设备关系的真实视图。后端已经持久保存账号与桌面设备关联及最近设备，但 Web 只在面试准备页读取 `last-used`，没有设备列表接口。

积分系统已使用 PostgreSQL 不可变账本计算余额，后台也具备独立管理员会话、权限、审计和配置页面。邀请奖励必须进入同一账本事实源，不能由浏览器或普通管理员接口直接修改余额。

## Goals / Non-Goals

**Goals:**

- 设备中心展示当前账号真实关联的设备以及彼此独立的在线、权限和面试连接状态。
- 提供可恢复的刷新、空状态、错误状态和诊断入口，不再展示合成设备。
- 为每个用户提供稳定、不可枚举的公开邀请码和分享链接。
- 保证每个被邀请账号最多激活一次、禁止自邀，并把激活关系与邀请人积分入账放在一个数据库事务中。
- 让授权管理员配置邀请功能开关和单次奖励积分，并保留审计记录。

**Non-Goals:**

- 本轮不改桌面助手协议、安装包、系统权限申请或面试 lease 行为。
- 本轮不为被邀请人额外发积分，不实现多级分销、现金返佣、排行榜或提现。
- 本轮不基于手机号、IP、设备指纹建立复杂反作弊画像；保留后续风控扩展点。
- 不把用户 ID、手机号、设备信息或奖励额度写进客户端可篡改的链接参数。

## Decisions

### 1. 设备中心读取账号设备列表，而不是准备页快照

后端新增当前账号设备列表接口，基于 durable account-device association 返回设备 ID、展示名、掩码机器码、平台、最近使用时间、最近心跳、在线状态和助手报告的权限/能力。当前面试连接作为可选摘要单独返回，不用一个 `connected` 布尔值推断其他状态。

替代方案是继续复用 `last-used`。它只能表达一台最近设备，无法支持“已连接设备”列表，也会把最近使用误解为当前在线，因此不采用。

### 2. 诊断首先做状态解释和恢复，不远程控制助手

设备页刷新会重新读取权威状态；每台设备展开诊断时显示最后心跳、各权限/能力和当前面试连接，并提供打开使用说明的恢复入口。网页不触发 macOS 权限请求，也不远程开始收音。

替代方案是让“诊断”直接修改权限或启动采集，这违反操作系统权限边界，也容易在没有活动面试时误收音，因此拒绝。

### 3. 邀请码是稳定随机公开标识

每个用户按需生成一个随机、URL-safe、数据库唯一的邀请码；分享链接使用 `/invite/<code>`，不包含可逆用户标识。已有邀请码长期稳定，复制链接不会重复创建记录。

替代方案是编码 user ID，容易枚举并泄露内部身份；每次生成新码则会造成历史链接失效，因此不采用。

### 4. 激活采用显式落地页或积分页确认后一次提交

访问邀请链接先展示邀请说明和“登录并激活”动作；未登录用户完成登录后恢复待激活邀请码，再由 Web 调用服务端激活接口。已登录用户必须从邀请落地页或积分与会员页明确确认。服务端是唯一判定者，前端缓存只用于恢复流程，不代表激活成功。

已登录且尚未激活邀请的用户也可以在积分与会员页粘贴完整分享链接或邀请码。Web 只负责从受支持的 `/invite/<code>` 路径或纯邀请码中提取候选值，并在用户点击确认后调用同一个服务端激活接口；浏览器解析或展示成功均不能代替服务端结果。成功后重新读取邀请状态，已激活或活动关闭时禁用该入口。

每个用户终身最多作为 invitee 成功激活一次；邀请人和被邀请人必须不同。重复提交同一关系返回原结果，尝试另一邀请码返回“已激活过其他邀请”。

### 5. 邀请关系和积分账本原子提交

PostgreSQL 增加邀请配置、用户邀请码和激活关系表，并扩展账本 kind 支持 `referral_credit`。激活事务按稳定顺序取得相关用户 advisory lock，读取启用配置和奖励快照，插入唯一激活记录与一条唯一账本记录后提交。任一步失败都不保留关系或积分。

这样可以复用现有余额计算和明细展示。替代方案是先写激活再异步加积分，会出现关系成功但余额未到账，也增加补偿复杂度，因此不采用。

### 6. 后台配置是持久化、受权限和审计保护的单例

后台新增“增长设置”，由 `growth.manage` 权限控制邀请开关和奖励积分，奖励必须为 1–100000 的整数。每次更新保存版本、操作者、时间和原因，并写管理员审计；用户端状态返回当前是否可激活和奖励额度，但不信任客户端提交的额度。

关闭功能时不删除邀请码、历史激活或积分流水，也不撤销已发奖励；新激活返回暂停状态。

## Risks / Trade-offs

- [批量注册账号刷奖励] → 现阶段依赖已验证账号、一次性 invitee 约束、自邀禁止、后台紧急关闭和审计；预留 IP/设备/注册时效风控字段但本轮不采集更多个人数据。
- [并发激活造成重复入账] → 数据库唯一约束、用户 advisory lock、同事务写关系与账本、唯一 reference ID。
- [设备刚离线仍显示在线] → 在线状态使用现有心跳 TTL，并展示最后心跳时间；刷新不伪造实时连接。
- [配置修改影响历史解释] → 激活记录保存奖励积分和配置版本快照，历史流水不随配置变化。
- [邀请链接被转发给非预期对象] → 邀请码不暴露身份；账号只在明确落地页操作后激活，且服务端返回邀请人脱敏展示名。

## Migration Plan

1. 先部署兼容数据库迁移、设备列表和邀请 API，默认关闭邀请奖励。
2. 部署 Admin 增长设置并由管理员填写奖励额度、确认后开启。
3. 部署 Web 设备中心、积分邀请卡和邀请落地页。
4. 使用合成账号验证自邀、重复激活、并发激活、关闭开关、积分流水及设备在线/离线状态。
5. 回滚 Web/Admin 时保留数据库表和账本 kind；后端接口可继续兼容，已发积分不撤销。

## Open Questions
