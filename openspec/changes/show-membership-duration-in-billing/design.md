## Context

Backend 已通过 `billing_time_pass_entitlements` 保存有效期，并在计费状态中返回 `activePass` 和 `queuedPasses`。支付成功时，同一事务会创建会员权益或将重复购买顺延。当前 Web 积分页虽然在积分卡底部显示到期日期，也能列出待生效权益，但卡片主数值始终是积分点数，导航名称也只有“积分”；支付轮询确认成功后只替换订单，不重新加载计费状态。

## Goals / Non-Goals

**Goals:**

- 让用户进入积分页后立即判断会员是否到账、剩余多久、何时到期。
- 同时呈现会员和积分，明确会员优先且积分不会因开通会员而消失。
- 在支付成功后自动显示新权益，并正确表达顺延购买。
- 使用服务端绝对时间作为事实源，前端只负责可读倒计时。

**Non-Goals:**

- 不改变会员价格、可购买天数、激活、顺延、退款或计费优先级。
- 不新增自动续费、会员等级或新的数据库字段。
- 不调整支付宝、微信支付协议和回调处理。
- 不修改桌面助手。

## Decisions

### 1. 使用一张“我的权益”卡并同时展示会员与积分

有效会员状态下，卡片主内容为“会员使用中”和“剩余 X 天 X 小时”，其下展示精确到期时间、回答/截图不扣积分的范围以及知识材料额度。积分余额以独立次级区域显示并注明“会员到期后继续使用”。无会员时，积分恢复为主数值，并明确显示“当前未开通会员”。

替代方案是只在现有积分数字下增加一行日期。该方式与当前实现接近，但仍无法解决用户第一眼只看到积分、无法判断会员是否到账的问题，因此不采用。

### 2. 剩余时长由 `endsAtMs - 当前时间` 派生

不持久化“剩余天数”，避免客户端缓存产生漂移。页面使用分钟级时钟更新展示；大于等于一天显示“X 天 Y 小时”，不足一天显示“X 小时 Y 分钟”。精确到期时间始终同时展示。到期边界触发一次计费状态刷新，以识别下一段待生效会员。

替代方案是只显示到期日期。它准确但不利于用户快速理解剩余权益，继续保留为辅助信息而非唯一信息。

### 3. 支付确认后重新读取 `/api/v1/billing`

在 Web adapter 增加读取现有计费状态接口的能力。订单轮询首次观察到 `paid` 后，重新读取并替换 `state.billing`，使服务端创建的 `activePass` 或 `queuedPasses` 立即出现。刷新失败时保留订单成功状态并显示“权益同步中”，不根据购买商品在客户端推算会员到期时间。

替代方案是前端用订单商品快照直接构造会员。该方案会绕过服务端顺延规则，也可能在回调事务未完成时展示虚假权益，因此不采用。

### 4. 统一入口名称但保持路由兼容

侧栏文字从“积分”改为“积分与会员”，路由继续使用 `/app/billing`，以避免书签、支付返回地址和历史链接失效。实时面试页仍保留紧凑入口，但文字也使用统一名称。

## Risks / Trade-offs

- [客户端时钟不准确导致倒计时偏差] → 以服务端绝对到期时间为准并同时展示精确到期时间；页面重新聚焦和到期边界时刷新事实源。
- [支付成功后状态读取短暂失败] → 明确显示同步中并允许重试，不在客户端伪造权益。
- [移动端权益卡信息过多] → 会员剩余时长优先，积分、额度和精确日期分层显示并增加响应式回归测试。
- [导航名称变长影响窄布局] → 复用现有侧栏宽度并验证紧凑断点，不改变图标和路由。

## Migration Plan

1. 先增加计费状态读取方法、剩余时长格式化函数及单元测试。
2. 改造积分页权益卡和导航文案，覆盖有效、无会员、待生效与到期状态。
3. 接入支付成功后的计费状态刷新并运行 Web 全量测试、类型检查和构建。
4. 仅部署 Web；如出现展示问题可回滚 Web 镜像，不影响后端会员权益和支付数据。

## Open Questions

无。首版按“剩余天/小时 + 精确到期时间”展示，不引入会员等级或自动续费。
