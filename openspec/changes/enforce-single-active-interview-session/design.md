## Context

当前系统分别具有 session 状态、桌面设备绑定、网页单页租约和实时发布器代际控制，但“新面试接管旧面试”隐含在设备绑定操作中。该时机过晚且没有用户确认，旧网页在异常重连时仍可能继续发起心跳和轮询，导致无效请求竞争实时语音资源。

## Goals / Non-Goals

**Goals:**

- 在准备页绑定设备前发现同账号的其他 live session。
- 通过服务端权威、幂等且带预期 session 校验的接管操作结束旧链路。
- 让旧页面、旧设备绑定、旧发布器和旧 ASR 工作队列尽快停止。
- 不改变资料、回答、历史记录、计费和桌面系统权限。

**Non-Goals:**

- 不删除旧面试历史或用户资料。
- 不允许一个账号并行运行多场实时面试。
- 不调整 ASR 模型、音频分片参数或回答生成链路。
- 不引入新的数据库表或分布式锁服务。

## Decisions

### 准备阶段先查询冲突

网页进入准备页后查询目标 session 之外的 live session。存在冲突时，资料仍可查看，但设备绑定和开始按钮被阻断，并展示“继续上一场”与“结束上一场并继续”。

替代方案是在点击开始时才检查；该方案无法阻止设备绑定提前静默接管，所以不采用。

### 接管使用带预期值的服务端命令

接管请求携带用户当前看到的旧 session ID。服务端再次读取 live session；若旧 session 已变化则返回冲突，让网页刷新窗口，避免并发页面误结束另一场新面试。重复提交且旧 session 已结束时按成功处理。

替代方案是网页依次调用旧 session 的 end API；该方案不能统一回收实时发布器，也存在部分完成状态，所以不采用。

### 实时服务负责回收运行时

RealtimeSpeechService 在结束旧 session 后，将旧桌面绑定标为 stale、关闭 publisher、关闭 ASR session 并清空帧队列。SessionService 的 start 操作额外拒绝第二场 live session，作为绕过网页流程的后端兜底。

### 旧页面通过状态错误停止

已结束 session 不再接受网页心跳。旧页面收到 409 后沿用现有 replaced/invalid-session 清理逻辑，终止 SSE、轮询、回答和截图请求。桌面助手连接键包含 binding generation，服务端换代后立即重建发布链路。

## Risks / Trade-offs

- [两个接管请求并发] → 使用 expectedPreviousSessionId 校验；状态变化返回 409，不静默结束新目标。
- [服务进程间仍可能存在极短竞态] → start_session 再次执行单活校验；后续迁移到多实例时可在数据库层增加用户级事务锁。
- [旧页面因网络断开未立即收到失效] → 心跳和实时接口均以 ended 状态拒绝，恢复网络后会停止；服务端运行时已先回收，不再消耗 ASR。
- [用户误操作结束旧面试] → 窗口明确展示旧面试标题，并提供继续旧面试的主路径。

## Migration Plan

1. 先部署兼容后端 API 与保护逻辑。
2. 再发布使用冲突 API 的网页端。
3. 重新构建桌面助手，使连接键包含服务端绑定代际。
4. 回滚时可先回滚网页；新增 API 不影响旧客户端。后端绑定保护与网页必须成对回滚，避免旧网页无法绑定。

## Open Questions

无。当前产品约束已明确为每个账号最多一场 live 面试。
