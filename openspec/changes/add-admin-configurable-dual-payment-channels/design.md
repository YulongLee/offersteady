## Context

线上当前运行持久化商品、订单、积分和权益账本，支付宝官方适配器与历史 MZFPay 适配器也已存在，但结账入口仍由单个环境变量选择提供方。`checkout_provider` 为空时支付安全关闭；支付宝商户参数尚未配置，MZFPay 历史订单只有过期和验签失败记录。管理平台已有加密服务、MFA、RBAC、审计和商品定价管理，可以复用这些边界承载支付配置，但不能把商户私钥下发浏览器。

微信支付和支付宝的官方接入模型不同：支付宝电脑网站支付返回官方跳转地址；微信支付 Native 下单返回短期 `code_url`，前端渲染订单二维码。两者最终都必须映射到同一个持久订单、回调审计、对账异常和幂等权益发放事务。

## Goals / Non-Goals

**Goals:**

- 同时提供微信支付官方 Native 与支付宝官方电脑网站支付适配器。
- 允许管理员独立保存、验证和启停两个渠道，支持零、一或两个渠道启用。
- 用数据库配置代替单一进程环境开关，同时把环境变量保留为首次迁移输入和紧急回滚手段。
- 对商户密钥加密保存并只返回掩码/配置状态。
- 保证订单创建、通知验签、金额和渠道隔离、权益发放及重复通知幂等。
- 以关闭状态部署，不影响当前线上账号、资料、面试、账务和兑换码功能。

**Non-Goals:**

- 本轮不开放退款、分账、企业付款、自动提现或发票。
- 不用后台按钮绕过渠道验证把订单人工设为已支付。
- 不把 MZFPay 当作新的用户可选渠道；仅保留历史订单读取和紧急代码回滚能力。
- 未提供真实商户参数时不伪造“支付验收通过”。

## Decisions

### 1. 渠道配置持久化为每渠道一条版本化记录

新增 `billing_payment_channel_configs`，以 `wechat` / `alipay` 为主键，保存 `enabled`、公开字段 JSON、加密敏感字段、配置版本、验证状态及更新审计元数据。订单继续保存 `provider`，并新增可选配置版本快照，使配置更新只影响新订单。

替代方案是继续使用 `.env.production`。环境变量适合部署密钥，但无法支持管理端独立启停、配置审计和双渠道并存，因此只保留为迁移/故障回滚来源。

### 2. 使用现有 Admin Fernet 根密钥进行字段级加密

管理 API 接收敏感字段后立即加密；GET 只返回 `configured=true`、末尾掩码或证书序列摘要。空字符串表示保持原密钥，显式 `clearSecrets=true` 才删除敏感配置。审计只记录字段名、配置版本和启停变化。

替代方案是返回原值方便编辑。该方案会把应用私钥和 API v3 密钥暴露到浏览器、代理和录屏中，因此拒绝。

### 3. 启用前执行静态完整性和加密材料校验

支付宝至少要求 APPID、应用私钥、支付宝公钥、卖家 PID、HTTPS notify/return URL，并验证 PEM/RSA2 材料可解析。微信至少要求商户号、AppID、商户 API 私钥、商户证书序列号、微信支付平台证书或平台公钥、API v3 密钥、HTTPS notify URL，并验证密钥/证书格式。配置不完整时允许保存草稿，但拒绝启用。

替代方案是保存即启用。错误密钥会把用户带入无法到账的支付流程，风险不可接受。

### 4. 结账按用户选择的 `channel` 解析独立适配器

用户端状态返回 `availablePaymentChannels`。创建订单时，`channel=wechat` 使用微信 Native，`channel=alipay` 使用支付宝电脑网站支付；若渠道禁用或不完整，在创建任何订单前返回 503。历史订单仍按订单 `provider` 查询和处理。

替代方案是服务器随机选择可用渠道。该方案无法尊重用户选择，也会让支付页面和订单审计不一致。

### 5. 微信支付使用 API v3 Native 与平台签名通知

服务端用商户 RSA 私钥签名 Native 下单请求；回调使用平台证书/公钥验签，并用 API v3 密钥解密资源。只有商户号、AppID、订单号、金额、币种和成功状态全部匹配时才调用现有 `process_payment_notification`。二维码只包含微信返回的短期 `code_url`。

替代方案是客户端 SDK 直接持有商户信息，违反密钥边界且无法保证到账权威性。

### 6. 管理操作使用独立 `payments.manage` 权限和近期 MFA

查看掩码配置需要 `billing.read`；保存、验证、启停需要新增 `payments.manage`，且沿用高风险操作的近期 MFA、原因、确认和幂等要求。超级管理员默认拥有该权限，其他角色不自动扩权。

## Risks / Trade-offs

- [商户证书轮换导致回调突然失败] → 支持先保存新配置并验证，再原子切换版本；订单记录配置版本，旧回调仍可使用保留期内旧验签材料。
- [数据库中的加密根密钥丢失] → 配置进入不可解密故障态并自动禁用，不回退明文；运维从安全备份重新录入。
- [双渠道同时开启增加运营复杂度] → 管理页分别展示就绪、启用、最近验证和错误状态；回调与订单按渠道隔离。
- [没有真实商户账号无法完成端到端验收] → 合成签名测试和线上关闭态先部署；只有真实小额支付验收通过后管理员才开启渠道。
- [后台误关闭渠道影响支付中的用户] → 关闭只阻止新订单，现有待支付订单和回调继续按订单渠道处理到过期。

## Migration Plan

1. 部署新增表和关闭态种子记录，不改变当前支付行为。
2. 部署兼容 Backend：优先读取数据库配置；无记录时仍保持关闭，不自动启用现有环境凭据。
3. 部署 Admin 支付设置页和 Web 动态渠道展示；两种渠道均关闭时继续显示“支付暂未开放”。
4. 管理员录入商户配置并完成静态验证；保持 `enabled=false`。
5. 在测试商户环境和真实小额生产订单中分别验证下单、回调、重复通知、金额异常与权益到账。
6. 按渠道开启，可先单开再双开；监控回调审计和对账异常。

回滚时先在管理端关闭渠道，再回退 Web/Admin；Backend 保留新表和回调兼容，不删除订单、账本、配置或审计数据。

## Open Questions

- 微信支付生产账户最终使用平台证书模式还是微信支付公钥模式；实现同时保留字段，但上线前只启用实际签约模式。
- 支付宝最终使用电脑网站支付还是同时开通手机网站支付；本轮保持现有电脑网站支付范围。
