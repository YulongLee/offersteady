## ADDED Requirements

### Requirement: 服务端创建微信支付 Native 订单
系统 SHALL 仅对已启用且配置完整的微信支付渠道创建 Native 下单请求，并 MUST 使用服务端商品快照、商户身份和商户私钥生成请求。商户私钥、API v3 密钥和平台验签材料 MUST NOT 返回客户端。

#### Scenario: 用户选择微信支付
- **WHEN** 已认证用户购买已上架商品且微信渠道已启用
- **THEN** 系统创建渠道为 `wechat` 的待支付订单，并返回该订单对应的短期微信支付二维码值、金额和过期时间

#### Scenario: 商户订单号满足微信 Native 约束
- **WHEN** 系统为微信 Native 支付创建新的商户订单
- **THEN** 发送给微信的 `out_trade_no` 必须为 6 至 32 个允许字符，且回调中的同一编号能够唯一定位本地订单

#### Scenario: 微信拒绝下单请求
- **WHEN** 微信 Native 接口返回参数、签名、商户身份或产品权限错误
- **THEN** 系统将本地订单标记为失败、保存不含密钥和签名的安全错误码，并向用户返回可恢复的渠道错误，不得留下带占位支付地址的待支付订单

#### Scenario: 微信渠道未启用
- **WHEN** 用户请求微信支付但渠道关闭或配置不完整
- **THEN** 系统在创建订单前拒绝请求，不生成占位二维码或虚假待支付记录

### Requirement: 微信支付通知必须完整验签和解密
系统 MUST 使用当前订单允许的微信支付平台证书或平台公钥验证通知签名，使用 API v3 密钥解密资源，并在发放权益前核对商户号、AppID、商户订单号、金额、币种和支付成功状态。

#### Scenario: 合法微信支付通知
- **WHEN** 后端收到签名有效、解密成功、身份和金额匹配且状态成功的微信通知
- **THEN** 系统以幂等事务将订单设为已支付并恰好一次发放积分或会员权益

#### Scenario: 签名或金额不匹配
- **WHEN** 微信通知签名无效、解密失败或金额与订单快照不一致
- **THEN** 系统不得发放权益，并记录脱敏回调审计和可运营的对账异常

#### Scenario: 重复微信通知
- **WHEN** 微信重复投递同一支付事件
- **THEN** 系统返回幂等成功结果且不得重复发放权益

### Requirement: 微信订单与其他渠道隔离
系统 MUST 根据订单记录的渠道处理微信通知、查询和展示，且 MUST 拒绝微信通知引用支付宝或历史 MZFPay 订单。

#### Scenario: 微信通知引用支付宝订单
- **WHEN** 微信回调中的商户订单号属于支付宝渠道
- **THEN** 系统拒绝入账并创建提供方不匹配的对账问题

### Requirement: 用户看到准确的微信支付状态
收费页 SHALL 将微信 Native 订单显示为订单专属二维码，并 SHALL 只以后端已验证状态展示到账结果，不得依据二维码扫码完成或浏览器状态直接发放权益。

#### Scenario: 用户完成扫码但通知尚未确认
- **WHEN** 用户已经扫码付款但后端尚未收到并验证成功通知
- **THEN** 页面继续显示待确认并轮询 OfferSteady 订单状态，不提前展示积分或会员已到账
