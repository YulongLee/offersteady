## Context

当前管理后台已有按 `Asia/Shanghai` 聚合的注册、活跃、面试、订单、支付金额和 AI 质量趋势，支付订单与渠道回调也是权威事实，但系统没有记录“用户从哪条推广内容进入”。因此现有数据只能回答全站增长，不能把访问、注册、使用和收入归因到牛客文章、小红书笔记、百度内容、抖音视频或某个营销活动。

推广分析涉及注册前匿名访问、注册后用户身份、桌面下载、面试使用和支付收入。它必须同时满足三个约束：采集失败不能影响用户主链路；归因必须能解释且不能重复计算收入；推广 URL 和分析数据不得成为手机号、令牌或面试内容的泄露通道。

## Goals / Non-Goals

**Goals:**

- 让运营人员按今天、昨天、7 天、30 天、90 天和自定义区间查看推广访问、注册、下载、使用、下单、支付和收入。
- 让每篇推广内容拥有独立、稳定、可停用的推广链接，并归属渠道和营销活动。
- 提供渠道、活动和链接三级比较以及同一获客 Cohort 的转化漏斗。
- 提供首次触点与末次非直接触点两种可解释归因，并保证一笔转化在一个模型下只计算一次。
- 复用现有用户、面试和支付权威数据，不复制或修改业务事实。
- 保证采集、聚合和后台查询与注册、面试、快答、截图和支付热路径隔离。

**Non-Goals:**

- 首版不对接巨量引擎、百度营销、小红书聚光等广告平台 API，不做广告自动投放或转化回传。
- 不做跨设备概率归因、手机号匹配、设备指纹或第三方 Cookie 跟踪。
- 不建设任意 SQL、拖拽 BI、自定义公式、用户行为回放或单用户画像。
- 不把“支付收入”描述为净利润；未录入成本时不计算 ROI。
- 不回填上线前无法证明来源的历史访问或历史用户归因。

## Decisions

### 1. 采用“渠道 → 活动 → 推广链接”的三级模型

核心实体为：

- `promotion_channels`：牛客、小红书、百度、抖音等稳定平台维度。
- `promotion_campaigns`：例如“2026 秋招推广”，包含目标、周期、预算和状态。
- `promotion_links`：对应一篇文章、一条笔记、一个视频或一个投放位，包含随机 slug、站内目标路径、内容名称和状态。
- `promotion_cost_entries`：按日期向渠道、活动或链接追加人工成本记录和冲正记录。

活动可以跨多个渠道，链接必须绑定一个渠道，并可绑定一个活动。渠道和活动决定分析分组，链接决定最细内容粒度。链接产生首个有效触点后，渠道和活动归属不可直接修改；分类错误时克隆新链接并停用旧链接，避免重写历史。

替代方案是只使用任意 UTM 参数。该方案创建成本低，但参数容易拼错、被篡改且无法安全停用，不适合作为后台权威维度，因此只把 UTM 作为可选导出/兼容字段，不作为事实主键。

### 2. 使用第一方短链接和安全跳转

推广地址采用同站点路径，例如 `https://www.mianshiwen.cn/r/{slug}`。slug 使用不可枚举随机值。服务端只允许跳转到后台配置的站内路径 allowlist，不接受请求参数提供任意目标地址，从根源上避免开放重定向和钓鱼。

跳转流程：

```text
平台内容中的推广链接
        │
        ▼
GET /r/{slug}
        │
        ├─ 校验链接 active / 时间范围
        ├─ 设置第一方匿名 visitor cookie
        ├─ 设置本次 click cookie
        ├─ 投递最小化 redirect-hit 事件
        └─ 302 到站内目标页
                  │
                  ▼
        页面可见并停留达到阈值
                  │
                  └─ 记录 qualified-visit
```

链接停用或不存在时跳转到安全的产品首页并显示统一失效说明，不暴露内部编号。采集队列异常时仍优先完成跳转。

替代方案是独立 `go.` 域名。它便于隔离流量，但会增加 DNS、证书、Cookie 跨域和运维复杂度；当前规模优先使用同源路径，后续流量增长后可保持 slug 协议迁移到独立域名。

### 3. 区分原始点击和有效访问，过滤平台预览机器人

牛客、小红书、搜索引擎和社交平台可能预抓取链接。系统分别统计：

- `redirect_hits`：所有合法短链接跳转次数，仅用于诊断。
- `qualified_visits`：页面真实可见并完成轻量确认的访问。
- `unique_visitors`：选定范围内按匿名 visitor 去重的有效访客。

推广总览和漏斗默认使用 `unique_visitors`，不得用原始跳转次数冒充真实用户。服务端通过已知 Bot UA、安全速率规则和页面可见确认标记机器人或预览请求；原始 IP 和完整 UA 不进入长期分析表。管理员预览链接时使用“不计入统计”模式，内部测试流量可通过受控 cookie 标记排除。

### 4. 使用随机第一方匿名标识，不做设备指纹

匿名 visitor ID 为服务端生成的随机不透明值，存入 `Secure`、`HttpOnly`、`SameSite=Lax` 第一方 Cookie，建议有效期 90 天；推广归因窗口默认 30 天。事件只保存 visitor ID 的服务端 HMAC 标识、link ID、时间、落地路径枚举、referrer host、设备大类和过滤状态，不保存原始 IP、完整 UA、完整 referrer URL或任意查询参数。

用户拒绝非必要分析标识时，短链接仍可跳转并只增加不可跨会话关联的聚合点击；系统不得因此阻止注册或使用。隐私政策和 Cookie 提示需要说明用途、期限和退出方式，正式上线前应根据实际运营地区完成合规复核。

替代方案是浏览器指纹或手机号匹配。它能提高归因覆盖但隐私风险高、解释性差，本方案明确不采用。

### 5. 注册后采用确定性身份绑定，获客归因一经确定不漂移

同源登录或注册请求可以读取匿名推广 Cookie。认证成功后，客户端或服务端发起一个幂等、可重试的 attribution claim，将 visitor 与内部 user ID 绑定；claim 失败不得回滚注册或登录。后续页面加载在发现待认领标记时可以补交。

用户的获客归因在首次注册时计算并锁定：

- `first_touch`：归因窗口内最早的有效推广触点。
- `last_non_direct_touch`：注册前最后一个有效推广触点。

用户注册后的下载、首次使用、下单和支付默认沿用该用户的获客归因。已有用户后来点击新推广链接只记录辅助触点，不覆盖最初获客来源；再营销归因以后单独设计。

这种设计牺牲了跨设备覆盖，但保证“这篇内容带来多少新用户和后续收入”的口径稳定。后台必须显示 `organic/direct` 和 `unattributed`，不得把无法关联的用户强行分配给某个渠道。

### 6. 业务转化继续以现有权威事实为准

推广系统不在用户主链路中自建第二套注册、使用或支付事实。各阶段定义为：

| 漏斗阶段 | 权威定义 |
| --- | --- |
| 访问 | `qualified_visit` 的去重 visitor |
| 注册 | `auth_users.created_at_ms` 且已完成推广身份绑定的去重用户 |
| 下载 | 服务端实际开始返回桌面安装包的去重用户/visitor；页面按钮点击单独标记，不冒充下载 |
| 使用 | 用户首次成功开始一场实时面试；可补充显示首次桌面绑定作为诊断指标 |
| 下单 | `billing_checkout_orders.created_at_ms` 的去重用户与订单 |
| 支付 | 渠道权威确认且本地状态为 `paid` 的订单 |
| 收入 | 已归因 paid 订单的 `amount_cents` 之和 |

退款能力完善后，净收入另立口径；首版明确显示“推广贡献实收”，不显示“净利润”。下载无法绑定登录用户时先关联 visitor，后续 claim 后再合并。

### 7. 采用 Cohort 漏斗，避免把不同人群的自然日总量相除

默认漏斗以“所选日期内首次有效推广访问的人群”为 Cohort，观察其在 30 天归因窗口内是否完成后续阶段。每阶段按 visitor/user 去重，一人多次访问、多场面试、多次下单不会让人数漏斗膨胀；订单数和收入作为旁侧业务指标单独展示。

最近 30 天 Cohort 尚未完全成熟时显示 `observing` 和剩余观察天数，不把未来尚未发生的转化视为最终流失。后台另提供“事件发生日趋势”，但不得与 Cohort 转化率混用。

### 8. 同时保存原始触点、确定性事实和日聚合快照

建议数据模型：

```text
promotion_channels
  └─ promotion_campaigns（活动可跨渠道，通过链接关联）
       └─ promotion_links
            └─ promotion_touchpoints
                  └─ promotion_identity_bindings ── auth_users
                                                   │
                                                   ├─ interview_sessions
                                                   └─ billing_checkout_orders
                                                            │
                                                            ▼
                                              promotion_attribution_facts
                                                            │
                                                            ▼
                                              promotion_metric_snapshots
```

关键表：

- `promotion_touchpoints`：最小化访问事实，按事件 ID 幂等，原始明细建议保留 180 天。
- `promotion_identity_bindings`：visitor 与 user 的确定性绑定以及首次/末次触点。
- `promotion_conversion_events`：只保存现有业务表没有的下载等最小化事件；注册、使用、订单和支付由权威表派生。
- `promotion_attribution_facts`：按 `conversion_type + source_record_id + attribution_model_version` 唯一，一笔订单在一个模型下只能归因一次。
- `promotion_metric_snapshots`：按自然日、模型、渠道、活动、链接聚合，长期保存；实时今天值读取有界事实查询。
- `promotion_cost_entries`：追加式成本和冲正，不直接覆盖累计成本。

上线前的历史用户、订单和面试可以回填为 `unattributed`，但不能伪造推广来源。所有快照记录统计版本和覆盖开始时间。

### 9. 归因采集与聚合不得阻断用户主链路

短链接跳转只同步完成链接校验与第一方标识设置；事件先写入有界 Redis Stream，再由独立 analytics worker 幂等落入 PostgreSQL。队列不可用时记录安全计数并继续跳转。

注册后的身份 claim 为独立幂等请求；失败可重试但不影响登录。注册、面试、订单和支付的归因由定时任务读取权威表生成，不在快答、ASR、截图或支付事务中增加同步远程调用。管理查询读取推广快照或有界索引，不扫描音频、转录或资料表。

替代方案是在每条业务请求中同步写推广事件。该方案数据更即时，但会放大数据库连接和热路径延迟，与当前性能目标冲突，因此不采用。

### 10. 后台按五个任务页面组织

1. **推广总览**：日期与归因模型筛选；UV、注册、激活、付费用户、订单、实收、成本、CAC、ROAS；趋势、漏斗、Top 渠道/活动/链接和数据更新时间。
2. **推广链接**：创建、复制、筛选、停用和查看单链接效果；展示渠道、活动、内容名称、目标页、状态、有效访问、注册、付费和收入。
3. **营销活动**：活动周期、目标、预算、实际成本、渠道构成、收入、ROAS 和漏斗；支持 draft/active/paused/ended。
4. **渠道分析**：牛客、小红书、百度、抖音等横向比较，展示 UV、注册率、激活率、付费率、CAC、收入与 ROAS。
5. **转化漏斗**：访问 → 注册 → 下载 → 使用 → 下单 → 支付，展示人数、阶段转化率、累计转化率、流失数及 Cohort 成熟度。

未录入成本时 CAC/ROAS/ROI 显示“成本未录入”，不得显示 0。ROI 定义为 `(推广贡献实收 - 已录入推广成本) / 推广成本`，ROAS 定义为 `推广贡献实收 / 推广成本`；两者均不是会计净利润。

### 11. 权限、审计和导出边界

新增权限：

- `promotion.read`：查看聚合分析和链接状态。
- `promotion.manage`：创建/停用渠道、活动和链接。
- `promotion.cost.manage`：追加成本或冲正成本。

管理端不展示 visitor ID、user ID、手机号或单用户访问轨迹。创建、修改、停用、成本录入和冲正均写管理审计；分析读取继续受现有管理端限流、并发和查询超时保护。首版不提供用户级 CSV；后续如需导出，只允许聚合维度。

### 12. 指标口径必须版本化并展示数据质量

推广页面返回 `generatedAt`、`timezone`、`attributionModel`、`modelVersion`、`coverageStart`、`freshness`、`excludedBots`、`unattributedCount` 和 `cohortState`。所有比例的分子分母均由服务端返回，前端不自行猜测。

链接、渠道、活动没有数据时显示空状态；采集或聚合延迟时显示 `delayed/partial`，不得把缺失值绘制成零。归因规则变化通过新模型版本重算，旧版本保留用于审计，不能静默改写历史报表。

## Risks / Trade-offs

- [平台预览机器人造成虚假访问] → 区分 redirect hit 与 qualified visit，漏斗默认只用有效 UV，并展示被过滤数量。
- [用户跨设备或清除 Cookie] → 标记为 unattributed，不使用设备指纹或手机号概率匹配；后台显示归因覆盖率。
- [最近 Cohort 转化率看起来偏低] → 显示 observing/mature 状态和固定观察窗口。
- [活动或链接归属被修改导致历史漂移] → 首个触点后冻结归属，使用克隆链接纠错。
- [成本录入错误] → 使用追加和冲正、权限隔离及管理审计，不允许直接覆盖历史总额。
- [归因采集拖慢站点] → Redis 有界队列、异步持久化、超时降级，注册/面试/支付只读取权威事实。
- [同一订单被多个渠道重复计算] → 归因事实唯一约束，报表必须绑定单一模型版本。
- [推广数据被误认为财务利润] → 只展示实收、成本、ROAS/ROI，并明确不包含退款、税费、渠道费和人力成本时的限制。
- [匿名标识形成隐私风险] → 随机第一方标识、字段最小化、明确期限、退出机制和删除联动，不采集敏感业务正文。

## Migration Plan

1. 增量创建推广实体、触点、绑定、成本、归因事实和快照表；不修改现有业务表的权威字段。
2. 部署关闭状态的推广 Backend 能力和 analytics worker，使用合成 Bot/访客/注册/订单数据验证幂等、隔离和统计口径。
3. 创建系统渠道 `direct/organic/unattributed`，回填可证明的历史注册、使用和支付为 unattributed，只标记覆盖状态。
4. 灰度启用 `/r/{slug}` 和有效访问采集，确认跳转性能、失败降级、Cookie/隐私文案与内部流量过滤。
5. 启用注册后 identity claim，核对同一用户重复登录、清除 Cookie、多个推广触点和跨浏览器场景。
6. 运行日聚合与 Cohort 归因，对指定合成订单逐项核对首次触点、末次非直接触点、收入唯一性和成本公式。
7. 向拥有 `promotion.read` 的管理员开放推广中心，只开放只读总览；观察数据完整性和数据库负载后再开放链接、活动和成本管理。
8. 回滚时先隐藏管理入口并停止推广采集/聚合；短链接继续安全跳转到原目标或首页。保留事实与快照表，不删除已有支付、用户或面试数据。

## Open Questions

- 推荐首版归因窗口为 30 天、匿名 Cookie 为 90 天、触点明细保留 180 天；正式开发前需要产品与合规共同确认。
- 推荐“使用”定义为首次成功开始实时面试；如业务更重视伴随程序激活，可在漏斗旁增加“首次设备绑定”，但不替换主漏斗阶段。
- 首版成本建议由管理员手工追加；广告平台自动拉取成本和服务端转化回传应在真实投放量出现后另立变更。
- 当前建议使用同源 `/r/{slug}`；只有独立推广域名、流量隔离或品牌需求明确后再迁移到 `go.mianshiwen.cn`。
