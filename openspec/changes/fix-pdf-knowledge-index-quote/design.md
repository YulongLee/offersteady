## Context

当前知识材料上传对话框用 `file.size / 4` 展示 Token 估算，`DocumentService.complete_upload` 和手动重试也用 `size_bytes / 4` 创建真实计费报价。这将容器格式的二进制开销误认为正文：相同内容的 PDF 通常远大于 MD，图片型或嵌入字体的 PDF 尤其严重。

系统已经具备可替换的 Parser、Markdown normalizer、OSS 规范化产物路径和版本化计费报价，因此修复应复用现有边界，不引入第二套 PDF 解析器或客户端可信计数。

## Goals / Non-Goals

**Goals:**

- 对所有格式按服务端规范化后的可索引正文统一估算 Token。
- 在积分或会员额度预留前展示最终服务端报价。
- 报价绑定用户和文档版本，防止跨文档复用。
- 复用预报价解析产物，避免 PDF 远程解析两次。
- 保持历史已确认报价及现有费率不变。

**Non-Goals:**

- 不改变知识索引的积分单价、最低消费或会员额度规则。
- 不更换 MinerU、Embedding 模型或向量数据库。
- 不为不可提取文字的扫描件在本轮增加新的 OCR 供应商；现有 Parser 能提取则计费，不能提取则明确失败且不扣费。
- 不重算或退款历史已结算索引。

## Decisions

### 1. 使用两阶段“上传并报价 / 确认并索引”协议

客户端先创建 upload intent 并上传原始对象，然后调用预报价接口。服务端确认对象、解析规范化正文并生成绑定 `documentVersionId` 的报价；客户端展示该报价后，第二次请求携带 `quoteId` 进行确认和预留。

替代方案是继续在浏览器估算 PDF，或在最终完成请求内解析并直接扣费。浏览器方案需要增加 PDF/DOC 解析依赖且仍无法保证与服务端一致；单请求方案无法在扣费前展示最终价格，因此不采用。

### 2. `mvp-v1` 按规范化 UTF-8 正文字节数估算

当前系统未引入模型专属 tokenizer。为保持可复现且不增加运行时依赖，统一使用 `ceil(len(normalized_markdown.encode("utf-8")) / 4)`，关键修复点是输入必须是解析后的正文而非原始容器。未来可通过 tokenizer 版本升级替换算法，历史报价仍保存版本快照。

### 3. 预报价产物写入既有 `normalized.md` 路径

预报价解析成功后保存规范化 Markdown。正式处理任务先读取同版本的 `normalized.md`，不存在时才调用 Parser。这样既降低 PDF 延迟和外部解析成本，又不新增数据库正文列。对象仍遵循用户隔离路径和既有删除任务。

### 4. 服务端验证报价与文档版本一致

确认接口只接受属于当前用户且 `documentVersionId` 与已确认上传对象一致的报价。BillingService 提供显式绑定校验入口，避免仅凭 `quoteId` 预留其他文档的报价。旧客户端无 `quoteId` 时服务端仍可完成安全解析，但返回“需要确认最终报价”，不直接静默预留。

### 5. 重试按缓存正文报价

手动重试从同一版本的规范化产物计算 Token，不再回退到原始文件大小。若缓存不存在则先重新解析；解析失败时不创建新预留。

## Risks / Trade-offs

- [预报价需要等待 PDF Parser，首次报价比本地瞬时报价慢] → UI 显示独立解析状态；正式索引复用结果，使总链路通常不增加一次解析。
- [预报价完成后用户不确认，会留下原始对象和规范化产物] → 沿用 upload intent/删除任务治理，并后续由过期清理回收；不产生计费预留。
- [UTF-8 字节近似不等同于具体模型 tokenizer] → 报价记录 `mvp-v1`，统一输入可先消除格式偏差，后续以新版本迁移。
- [旧客户端没有两阶段协议] → 明确返回需要展示的最终报价而不是静默扣费；Web 同版本发布。

## Migration Plan

1. 先发布兼容新增字段和预报价接口的后端。
2. 发布使用两阶段协议的 Web 客户端。
3. 新报价全部使用规范化正文；历史已确认和已结算报价保持不变。
4. 回滚时可恢复旧 Web 流程，但后端不得恢复按原始二进制大小计费。
