## Context

公开首页已有“联系我们”区域，实时面试页则以高密度核心操作为主，没有适合常驻展示多行联系方式的空间。本次新增的抖音号和小红书号是公开产品账号，不需要后端读写、用户数据或平台授权。

## Goals / Non-Goals

**Goals:**

- 首页直接展示新增的两个官方账号。
- 实时面试页通过轻量、按需展开的入口提供相同联系方式，不挤占对话与回答空间。
- 两处使用同一份前端常量，防止账号文案漂移。
- 保持现有微信、邮箱、服务时间及面试链路完全不变。

**Non-Goals:**

- 不增加抖音或小红书的深链、二维码、关注状态或私信能力。
- 不扩展后端支持配置模型或管理后台。
- 不修改使用手册、计费页、法律页或静态 SEO 联系页。

## Decisions

### 1. 将公开社交账号定义为共享只读展示数据

在 Web 展示层建立共享的社交账号列表，首页和实时面试页从同一列表渲染。相比在两个 JSX 区域分别硬编码，该方式能保证标签和值一致；相比扩展计费支持配置，它不会为两个已明确且固定的公开账号引入不必要的 API 和配置迁移。

### 2. 首页直接展示，实时面试页按需展开

首页在现有联系信息定义列表中增加“抖音号”和“小红书号”。实时面试页在头部操作区提供紧凑的“联系我们”详情菜单，展开后显示两个账号；移动端复用现有“更多面试操作”菜单中的联系方式分组。相比把两行账号常驻放入实时工作区，此方案更少干扰核心面试内容和响应式布局。

### 3. 仅展示账号文字

当前只提供账号名称，不猜测未经确认的平台主页 URL。页面提供可选择、可复制的文本，不生成可能失效或指向错误主体的外部链接。

## Risks / Trade-offs

- [实时页新增入口增加少量头部信息密度] → 使用折叠菜单，并在窄屏放入既有更多菜单。
- [固定前端账号未来修改需要发版] → 两处集中读取同一常量；需要后台配置时再单独设计迁移。
- [同名账号可能被仿冒] → 只展示用户确认的名称，不添加未经核验的主页链接或认证声明。
