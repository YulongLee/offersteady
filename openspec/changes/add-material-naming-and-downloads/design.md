## Context

文档服务已经持久化 `display_name`、`original_filename`、内容类型和私有对象键，但上传完成时直接把原始文件名写入展示名称，所以同名文件在资料管理和面试准备中无法区分。知识资料重命名目前只更新前端内存，刷新即丢失。对象存储具备按私有键读取原文件的能力，但没有面向资料所有者的下载接口。

## Goals / Non-Goals

**Goals:**

- 所有资料清单中的活动资料名称稳定且可区分。
- 新上传的同名资料从写入时即获得唯一展示名称，现有重复数据无需离线停机迁移也能正确展示。
- 简历、JD 和知识资料使用同一套持久化重命名规则。
- 用户只能下载自己未删除资料的原始文件，并获得正确的下载文件名和内容类型。
- 资料库页和面试准备页都能直接下载资料。

**Non-Goals:**

- 不修改对象存储键、解析产物、向量索引或历史回答中的资料快照。
- 不提供公开分享链接、跨账号下载、批量打包下载或在线编辑文件内容。
- 不自动修改用户自定义过的名称，也不物理重写原文件。

## Decisions

### 1. 展示名称与原始文件名继续分离

上传时以原始文件名为候选展示名称，在同一用户和资料类型范围内按不区分大小写的方式检查冲突，并在扩展名前追加 ` (n)`。下载仍使用不可变的 `original_filename`，重命名只改变 `display_name`。

选择这一方案是因为展示名称属于用户管理元数据，不应改变原文件身份或对象键。备选方案是上传时重命名原文件，但会破坏用户取回文件时的预期。

### 2. 历史重复数据在服务层稳定消歧

清单返回前按创建时间和文档 ID 建立稳定顺序；相同资料类型、相同展示名称的第二份及以后资料在响应中追加编号。新上传和用户重命名会持久化唯一名称，因此响应期消歧主要兼容历史数据。

选择无停机的兼容层，而不是立即编写不可逆数据库批量迁移，避免影响历史回答快照和当前原型环境中的内存存储。后续可以在确认线上数据后将兼容结果回填。

### 3. 下载通过账号鉴权的后端响应

新增资料下载端点。服务端先按当前账号验证文档归属与删除状态，再从存储读取原始字节，以保存的内容类型和 RFC 兼容的 `Content-Disposition` 返回附件。浏览器不接触对象键或长期 OSS URL。

选择后端代理下载是为了统一支持本地内存存储和 OSS，并避免私有对象地址泄露。20 MB 的现有上传上限使单次响应内存成本在原型阶段可接受；未来如上限提高再切换为受控流式代理或短时签名地址。

### 4. 前端下载使用带登录令牌的 Blob 请求

资料适配器使用现有认证令牌请求下载端点，从响应头解析文件名并创建一次性 Blob 下载。面试准备选择项中的下载按钮阻止事件冒泡，下载不会改变资料选择状态。

## Risks / Trade-offs

- [并发上传同名文件可能同时选择相同编号] → 当前保存仍以文档 ID 为主，不丢数据；服务层清单消歧保证界面可区分，后续可增加数据库唯一约束。
- [代理下载占用后端内存] → 沿用 20 MB 文件上限，并拒绝已删除或不存在对象；未来文件上限提升时改为流式响应。
- [历史回答中的资料名仍可能重复] → 历史快照保持不可变，只有当前资料清单使用消歧名称，避免篡改已有回答来源记录。

## Migration Plan

1. 先发布兼容的后端接口与清单消歧逻辑。
2. 再发布前端重命名和下载入口；旧前端不依赖新字段，能够继续使用。
3. 通过合成同名资料验证历史清单、新上传、重命名、下载和越权场景。
4. 回滚时移除前端入口与新增路由即可；既有 `display_name` 更新仍是合法元数据，不需要回滚。

## Open Questions

无。当前范围按账号和资料类型消歧，满足面试准备页跨知识库聚合展示的需要。
