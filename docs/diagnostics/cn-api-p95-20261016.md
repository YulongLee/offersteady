# 国服 API P95 再次超过一秒：2026-10-16

用户反馈今天下午 API P95 超过一秒。本次仅对国服实际容器、容量样本、日志与诊断接口作只读排查，没有修改应用或配置、重启、部署、压测或创建真实面试。

## 结论

今天的秒级高峰属实，峰值出现在北京时间 **15:51:10，1,106.14ms**。最大慢尾贡献路由是高频 `performance-ack` 性能上报；心跳、设备轮询及状态读取也同时变慢，实际回答启动受到影响。不能将其解释为只有仪表盘数字变高。

昨晚的预取补丁仍在线，相关三文件 SHA 与[发布记录](../releases/cn-question-prefetch-20261015.1.md)完全匹配，调度合并确实执行。但它只降低了一个后台工作来源，没有覆盖高频上报的通用鉴权读写、轮询和同步状态/资料读取。真实字幕节奏下仍有持续检索，这些工作与用户请求共享后端资源。

现有证据确认了慢尾来自哪些接口，以及未优化的具体源码成本；**尚无逐请求 SQL、建连、线程池或事件循环分阶段计时，不能声称已量出某条 SQL/数据库锁或某个执行器是唯一根因。**

## 已核对的剩余成本

实际容器的 deps、authentication service、Postgres authentication repository、realtime/web/session modules 六文件 SHA 均与已保存实际源候选一致。

1. 带有效 Bearer 的请求在进入 ACK 会话归属缓存前，仍执行通用登录鉴权：读取 auth session、读取用户、读取身份绑定、更新 auth session 的 last-used 时间。仓库对应四次独立 PostgreSQL 连接/查询或提交，没有复用连接池；同一登录会话的并发请求还更新同一行。这是已确认工作量，未测得其各阶段延迟占比。
2. ACK 仅 transcript-render 阶段可使用 60 秒会话正缓存；其它阶段仍读取完整面试及资料。现有日志没有 ACK stage 分布，不能断言多少缓存未命中。ACK 本体是短内存 trace 更新，不做 Redis XADD/trace 回写，不应解释成 Redis 回写慢。
3. ACK 使用默认同步执行池；heartbeat/active-connection 使用独立控制执行器。累计控制执行器 saturated 0 不代表没有队列等待，也不能代表 ACK 的默认池没有等待。
4. 部分 async 状态接口直接调用同步数据库逻辑；web/state 涉及账单、资料和历史会话，session list/get/idle-status 会刷新绑定资料。这些路径存在阻塞事件循环并拖慢其它请求的风险，但本次未直接测量 loop lag。

## 资源与错误边界

超过一秒的十个容量样本：CPU 7.66%–46.66%、内存 6.25%–6.30%、数据库连接 1–2/100、5xx 率零。没有内存或连接配额耗尽证据；瞬时连接数低也不能排除频繁建连和同步读取成本。

15:55 后实时工作量和检索回落，综合 P95 回落约 100ms。下午 12:00 至日志取证结束的 87,531 条普通请求整体 P95 为 271.37ms，390 条达到一秒；这不是全天 P95，也不能用整体值否定局部峰值。独立 access 日志未发现 5xx，但存在 401/404/409 等响应；request.completed 无状态，不能给每条慢请求虚构状态。

## 下一步优先方向

优先围绕高频 ACK/控制链减少重复鉴权读写与 last-used 持久化频率，并保护退出登录、撤销、权限和限制状态的及时生效；同时核对前端上报合并、状态读取轻量化及同步 IO 隔离。补充分阶段计时与用户/遥测分类，使后续能比较用户体验而非只看综合值。本次没有实施这些行为变化，也没有改线上指标口径。
