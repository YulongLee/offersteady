# 国服 API P95 上升诊断（2026-10-14）

## 范围与结论

只读检查北京时间 2026-10-14 00:00–约 23:18 的 Backend 日志、最近六小时 Redis 容量样本、实际运行镜像和历史保留镜像。未压测、创建收费面试、调整配置、重启或部署生产服务；本文只保存脱敏汇总和源码证据。

最明显的高延迟出现在 16:00–16:15。已确认一个性能回归：10 月 10 日上线的页面心跳轻量化，在 10 月 11 日笔试会员增量镜像中被旧心跳方法覆盖。频繁的稳定字幕上下文预取、设备轮询和遥测请求进一步增加高峰工作量。延迟存在于多类用户与控制 API，不能将所有峰值归因于单一模型调用、整机 CPU 耗尽或纯粹指标显示问题。

## 主要证据

### 1. 已发布的心跳优化被后续方法覆盖

当前实际 Backend 镜像为 `offersteady-cn-backend:written-exam-pass-20261011-1`，digest `sha256:567ddaf392216bad2b23644cf94f65b8b4c0b5f9cb982e6ae15be8891cac06e1`。

对比切换前保留的轻量镜像 `sha256:2728cf3959771f813fcf7ea9fe86395ff1b94f731c3b5288a4decde65c66d496`：

- 轻量镜像的 `record_web_session_heartbeat` 使用 `heartbeat_idle_status`，只读五字段会话投影。
- 当前方法先 `reconcile_idle_session → idle_status → get_session`，再显式调用一次 `get_session`，正常心跳重新执行两次完整会话读取。
- `get_session` 每次调用 `_refresh_bound_document_activity`，逐个 `document_repository.get_by_id` 刷新绑定资料。Postgres 仓库按次建连接、读取会话及资料。五字段投影方法仍存在，但心跳入口没有使用它。

此回归不属于 [笔试会员需求](../../openspec/changes/make-written-exam-pass-inclusive/design.md) 的范围，且不符合 [轻量心跳场景](../../openspec/changes/lighten-cn-web-heartbeat/specs/lightweight-web-heartbeat/spec.md)。历史 [10 月 10 日发布证据](../releases/cn-web-heartbeat-lightweight-20261010.1.md) 不能替代对运行镜像的核对。

### 2. 稳定字幕预取产生持续的额外检索

运行源码的 `_observe_stable_interviewer_partial` 在系统声源的稳定文字长度达到四字且变化时提交 `question_prefetcher`。注入的 `ChatService.prefetch_question_context` 对新 revision 读取会话并检索；没有按时间防抖或同问题并发合并。较旧 revision 可以在提交前被跳过，但已经开始的检索仍执行，只在保存结果时再次判定 revision。

16:00–16:15 有 475 次成功检索、468 个不同问题哈希，而正式文字回答启动 56 次、截图启动 15 次。17:00–17:25 有 459 次成功检索、14 次文字回答启动；检索 P50 965 ms、P95 1,307 ms。

全天扫描有 5,004 次成功检索、4,845 个不同问题哈希；精确重复 159 次（3.2%）。应描述为“不断变化的稳定字幕触发大量预取”，不能称为大量完全相同查询的重复执行。检索全天 P50 896 ms、P95 1,346 ms。日志未直接标记每次检索的预取来源，预取占主导是结合调用图及检索/正式回答量推断；心跳资料刷新本身不直接调用向量检索。

### 3. 高频控制与遥测放大工作量，用户接口也变慢

17:00–17:25 的 12,484 次完成请求中，active-connection 3,750 次、performance-ack 3,497 次、设备心跳 2,624 次，合计约 79%。这些接口与较重会话读取共享后端及数据库资源，多个路由同时出现秒级慢尾。

21:25–21:35 仅五次成功检索，web-heartbeat 仍有约两秒的路由 P95，页面状态/历史读取也偏慢；该时段容器总 CPU 中位数约 3.89%，说明预取和总 CPU 不是所有峰值的唯一解释。

当前容量实现没有 `userApiP95Ms`、`telemetryP95Ms` 或路由级 `requestBreakdown`。综合 P95 混合用户业务和后台控制/遥测；但本次日志证实用户页面状态及历史读取确实有延迟，不能只解释为遥测影响数字。

## 资源与错误边界

- 17:08 容量 CPU 为 37.66%，17:07–17:09 附近有 41%–42% 样本。该值是 cgroup 用量除以可用核数；服务器四核、无 CPU 配额，不能将先前 Docker 约 100% 的单核等价值称为整机 CPU 耗尽。本次未发现 CPU throttling 证据。
- 保留窗口内内存约 20%–22%，数据库采样连接数通常 1–4 / 配额 100；没有证据支持内存耗尽或连接配额用满。低瞬时连接数不能排除频繁建连、串行读取或执行器等待的成本。
- 16:00–16:15 访问日志：200 为 6,324 次，409 为 87 次，404 为 36 次，401 为 9 次，307 为 1 次，无 5xx；结构化日志没有 ERROR。`apiErrorRate=0` 仅指 5xx，不代表没有鉴权/生命周期类 4xx。
- 没有历史逐请求执行器等待/SQL阶段耗时，因此无法精确量化心跳回归、预取和其它共享资源等待各占多少。

## 后续修复顺序

1. 先在实际运行 Backend 上最小恢复轻量心跳方法，保留笔试会员、模拟面试、计费及其它既有能力，执行既有回归与候选镜像检查。
2. 再按 OpenSpec 确认预取限频/合并和过期任务抑制，保留最终问题及正式点击回答的正确检索。
3. 补齐用户/遥测/慢路由分项，针对轮询、状态与历史读取继续缩减重复工作；不要仅靠调整指标口径或盲目增加线程/worker 宣称修复。

当前 Web 已恢复 `pricing-copy-hourly-20261011.1`，10 月 14 日状态去重候选因遗漏模拟面试路由而撤回，见 [Web 发布状态](../releases/cn-web-state-dedupe-20261014.1.md)。需要纠正此前“所有已发布优化仍保留”的判断：功能可访问与性能补丁仍生效是不同检查。
