## 实现与服务影响

1. 单场结束通过现有owner/session定点获取绑定，避免先列出全站或用户全部历史再筛选。用户的绑定、账号设备列表分别通过owner引用索引读取canonical记录，保留排序、stale历史、generation、退役和原始JSON精度。正常命中不执行全站HVALS/HGETALL/HSCAN，也不逐个检查无关用户的退役状态。
2. 两份引用索引及完整性计数在Redis脚本中与canonical写入同步维护，沿原共享运行态TTL延续。每个仓库初始化时原子重建，兼容空闲回退到旧writer后重新启动候选。常数长度校验及owner计数检查局部损坏；请求中不通过全站扫描偷偷修复或返回缺失历史。完全过期且canonical为空时可正常读空和接受新写。
3. CN普通实时服务使用可选关闭能力：先完成原会话结束、计费与退役、逻辑分离旧ASR连接，然后把旧对象的物理关闭握手交给独立2线程、8排队槽执行器。整场旧source一次性分离，迟到事件停止接受；后台任务只持有旧连接，不能按session键误关新对象。满载或停止接纳时同步关闭，接受的任务不丢弃、不中途取消；关机排空，失败仅记录固定计数。原同步gateway方法、旧gateway、Global及mock调用路径保留。
4. publisher prepare/create使用独立2线程、8排队槽准备通道；原ingress 4+16和lifecycle 2+8保留。仍按同场清理锁串行处理控制操作，取消后已创建publisher只补偿一次，结束后的迟到恢复不能复活会话。
5. CN性能回执使用已有权威control投影检查归属，不再为无内容的遥测装配简历与知识库。已有缓存期限、只对transcript-render使用的缓存边界、跨owner拒绝、所有字段/阶段/上报频率保持。INFO级别跳过无用DEBUG日志序列化；回执及trace记录仍保留。

本轮减少的是**一次请求内部的Redis往返、资料装配和排队拖累**，没有减少网页API请求数量，没有改变模型能力、字幕频率、面试权益或积分扣除方式。资源容量有界，过载时保留等待，不能承诺任何并发下结束接口都立即返回。
