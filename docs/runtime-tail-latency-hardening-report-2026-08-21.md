# 容量监控与面试链路长尾治理报告（2026-08-21）

## 结论

本轮修复了容量监控快照与数据库约束不一致的问题，并降低了实时面试 SSE 在长事件流和大量空闲连接下的 CPU、Redis 命令与线程池放大风险。改动不改变转写、问题确认、快答、截图回答或回答生成的产品语义。

## 容量监控修复

- 新增幂等数据库迁移，使 `admin_metric_snapshots.granularity` 同时接受 `capacity_5m`、`hourly` 和 `daily`。
- 迁移已接入后端启动迁移清单；重复执行不会改变现有数据。
- `capacity_5m` 峰值继续使用最大值单调 upsert，同一时间桶中的并发峰值不会被较小值覆盖。
- 持久化失败不会中断采样循环；管理端样本会标记 `capacityPeakPersistence=degraded`。
- 同类写入错误日志按五分钟限频，避免数据库异常期间形成日志风暴。

## 实时面试长尾治理

- Redis Stream 增加有界 `cursor -> stream id` 索引，正常增量恢复不再完整扫描历史事件。
- 阻塞等待直接消费 `XREAD` 返回的增量事件，不再在唤醒后重复读取整条 Stream。
- 老版本 Stream 首次读取时自动回填索引，后续走有界读取；游标超出保留窗口时明确要求客户端恢复快照。
- 网页面试 SSE 和桌面截图 SSE 使用独立等待线程池，空闲长轮询不会占满普通同步 API 使用的默认执行器。
- SSE 根据事件类型刷新运行态、转写和候选问题；截图、回答等事件不再触发完整历史事件重读。
- 运行态所需的最新 `device-status`、`degraded` 事件增加 Redis 快照缓存，避免周期性运行态刷新再次扫描事件历史。

## 合成性能证据

测试条件：保留 1,000 个事件，执行 200 次增量读取；数据是进程内合成基准，用于比较算法和命令放大率，不等同于线上网络 SLA。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 增量读取 P50 | 2.628 ms | 0.624 ms |
| 增量读取 P95 | 2.762 ms | 0.655 ms |
| 增量读取 P99 | 2.882 ms | 0.782 ms |
| P95 降幅 | - | 约 76% |
| 正常增量完整 `XRANGE` | 每次扫描 | 0 次 |
| 200 次空闲等待 `XREAD` | 不适用 | 200 次 |

在 8 个模拟阻塞等待存在时，普通默认执行器任务仍为 P50 0.028 ms、P95 0.044 ms、P99 0.072 ms，说明事件等待已与普通 API 的执行资源隔离。

## 部署与回滚

- 数据库迁移为扩展允许值，不删除数据。回滚应用版本时可以保留新约束；无需收窄回旧约束，否则仍会恢复 `capacity_5m` 写入失败。
- `OFFERSTEADY_REALTIME_EVENT_WAIT_WORKERS` 默认 32，可按在线 SSE 连接数与实例资源调整。若出现资源异常，可先下调该值并滚动重启。
- Redis 新索引和最新事件缓存均带运行态 TTL，删除这些派生 key 只会触发一次兼容回填，不影响原始 Stream。

## 仍需线上验收

本地无法替代生产环境的 30 分钟持续面试和真实并发压力。上线后应至少观察：

- 后端进程 CPU P50/P95/P99 与是否再次接近 96%；
- 健康检查、会话运行态、事件 SSE、音频帧和截图任务 API 的 P95/P99；
- Redis `XRANGE`、`XREAD` 调用量和慢命令；
- 默认执行器与事件等待执行器的排队量；
- `capacity_5m` 写入成功率、`capacityPeakPersistence` 状态和数据库错误日志量；
- 连续 30 分钟单场面试，以及逐级并发场景下是否出现 10 秒以上长尾。

未完成上述生产压测前，可以确认代码层面的已知放大因素已治理，但不能据此宣称已消除所有 51–109 秒线上长尾。
