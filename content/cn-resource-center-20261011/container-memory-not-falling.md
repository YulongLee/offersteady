## 先说结论：面试结束不等于 RSS 立刻归零

容器指标常见的是进程 RSS 或 cgroup 使用量。Python 对象被释放后，内存分配器可能把空闲块留在进程地址空间中，后续继续复用；操作系统也不一定马上把所有页归还给宿主机。因此，业务对象已经释放，RSS 仍可能停留在较高水位。

但“分配器复用”不能解释无限增长。如果每场面试结束后水位都持续抬高，且经过足够空闲时间、垃圾回收和多场重复测试仍不稳定，就需要进一步排查缓存、任务、连接、队列和全局引用。

## 容器图表到底测到了什么？

先确认指标口径：

| 指标 | 说明 | 能否直接证明泄漏 |
| --- | --- | --- |
| RSS | 进程当前驻留在内存中的页 | 不能单独证明 |
| Python 对象数量 | 仍由运行时管理的对象 | 需要按类型和快照比较 |
| cgroup memory current | 容器组当前使用量 | 需结合缓存和页缓存解释 |
| tracemalloc | Python 分配热点 | 看不到全部原生库分配 |
| 工作集/峰值 | 一段时间内使用过的峰值 | 更适合看容量上限，不等于当前活跃对象 |

“面试前 32.5%，结束后 33.3%”这个差值本身不能定性。需要同时观察空闲 10–30 分钟、下一场是否复用这部分内存、连续多场的基线是否线性抬升。

## 五类更值得优先检查的对象

### 1. 会话上下文和历史事件

面试上下文、问题、回答、转写片段、截图结果如果被全量保存在进程字典、任务闭包或长生命周期缓存中，结束后就算前端看不到，后端仍可能持有引用。

检查结束路径是否清理：会话对象、事件订阅、SSE 连接、临时列表、异常重试任务和与用户绑定的缓存 key。清理动作要幂等，即重复执行不会误删下一场面试的数据。

### 2. 异步任务和后台队列

模型调用、音频处理、PDF 解析、报告生成等任务可能在面试结束后仍未完成。若任务保留大对象作为闭包变量，或者失败后不断重试，内存会跟着任务数量增长。

排查任务总数、运行中/等待中/失败重试数，并为每类任务设置超时、取消和最大重试次数。结束会话时，应该取消只属于该会话的可取消任务。

### 3. Redis、数据库和 HTTP 连接

客户端连接池通常会保留连接，连接池变大不一定是泄漏；但每场面试都创建新客户端、未关闭响应体，或连接池没有上限，就会造成真实增长。

检查客户端是否按进程复用、连接池是否有明确上限、异常路径是否关闭响应流。监控连接数、池中空闲连接和等待连接，不要只看容器内存。

### 4. 文件、音频和图片缓冲

上传 PDF、截图和音频时，内存中可能短暂存在完整 bytes。若解析器、图片库或音频库创建了原生缓冲，Python 垃圾回收不一定马上反映在 RSS 上。

大文件尽量流式读取，限制单文件大小和并发数；完成后关闭文件句柄，删除临时文件，避免把 bytes 放进全局缓存。对原生库分配，结合进程级 RSS 和任务级样本观察。

### 5. 监控采样与日志缓冲

管理端监控如果每次采样都把历史数据拼成大列表，或者日志队列无人消费，也会让内存持续抬高。采样应使用固定窗口、固定数量和明确 TTL；日志应有容量上限和丢弃策略。

## 一套不改业务的验证流程

1. 记录空闲基线、单场峰值、结束时读数，以及 10、20、30 分钟后的读数。
2. 连续执行 3–5 场相同规模的合成面试，观察每场结束后的最低水位是否越来越高。
3. 同时记录活跃会话、后台任务、Redis key 数、数据库连接、文件句柄和事件循环任务数。
4. 使用 `tracemalloc` 对比两个稳定时间点的 Python 分配快照；再用 RSS 和容器指标补上原生库与页缓存部分。
5. 只对能复现增长的对象加释放或上限，并用回归测试验证“面试结束后仍能创建下一场”。

## 什么情况更像真实泄漏？

- 面试数量和内存水位近似线性增长；
- 长时间无面试，RSS 仍持续增长；
- 同样的面试规模重复后，每次最低水位都抬高；
- 会话已结束，但任务、连接、订阅或缓存数量没有减少；
- 达到容器上限后出现 OOM、重启或请求失败。

如果只是在第一场或前几场升高，随后稳定在可接受的水位，且下一场没有继续放大，可能是运行时预热、连接池或分配器复用。仍然需要设定容量上限和告警，不能仅凭“看起来正常”放任增长。

## FAQ

### 能不能在每场面试后强制把内存归还给系统？

可以尝试释放引用、触发垃圾回收或在特定场景使用进程隔离，但不应把“RSS 归零”作为业务正确性的唯一标准。频繁强制回收会增加 CPU 抖动；进程隔离和滚动回收则需要评估启动成本。

### 机器升级后问题会消失吗？

更大内存只能延后达到上限，不能修复未关闭的任务、无界缓存或连接泄漏。升级可以作为容量缓冲，但应与对象生命周期和增长曲线排查一起做。

### 如何避免文章把正常复用误判成泄漏？

不要只比较“面试前”和“刚结束”两个瞬时点。至少看一个空闲窗口、连续多场和相关资源计数，并区分 RSS、Python 对象和容器 cgroup 指标。

## 结论与下一步

面试完成后，业务对象应该解除引用、任务应该停止、连接和临时文件应该按生命周期处理；但容器 RSS 不一定立即回到面试前的数字。合理的判断方式是：看增长曲线是否稳定、关联资源是否回收、下一场是否复用，以及是否触发 OOM 或服务异常。
