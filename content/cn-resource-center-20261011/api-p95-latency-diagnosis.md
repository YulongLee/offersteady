## API P95 是什么？

API P95 是一段时间内请求耗时的第 95 百分位。简单说，如果把 100 次请求按耗时从小到大排列，P95 大约落在第 95 个位置：95% 的请求不超过这个数，最慢的 5% 会被它反映出来。

它不是平均值的替代品，而是用来观察长尾。平均耗时可能只有几百毫秒，但少量排队、慢查询或上游重试就能把 P95 推到 1 秒甚至更高。面试辅助、文件解析和实时会话这类混合业务尤其容易出现这种现象。

本文不把某一次线上读数当成固定结论，而是给出一套能复现、能验证的拆解方法。

## 先确认：是所有接口变慢，还是少数接口拖高了总指标？

第一步不要直接重启服务，也不要只盯着总 P95。先按路由、状态码、请求来源和时间窗口拆开：

| 维度 | 要回答的问题 |
| --- | --- |
| 路由 | 哪几个 endpoint 的 P95 最高？ |
| 流量 | 高 P95 的接口是否也是请求量最大的接口？ |
| 状态码 | 慢请求最后成功、超时，还是返回 5xx？ |
| 来源 | 普通页面、伴随程序、后台监控还是定时任务？ |
| 时间 | 延迟只在面试高峰出现，还是空闲时也持续？ |

如果只有一个低流量接口很慢，总体 P95 未必会明显升高；反过来，一个每秒被反复调用的轻量接口即使只慢几百毫秒，也可能主导整体指标。

## 把一次请求拆成五段

推荐为每个关键接口记录至少五个时间点：

1. **请求进入到开始执行**：看线程池、协程调度或连接池是否排队。
2. **业务代码执行**：看是否重复解析、重复读取历史数据或等待锁。
3. **数据库访问**：记录查询耗时、连接等待、返回行数和是否命中索引。
4. **Redis 或消息系统**：区分单次命令、批量读取、阻塞等待和重试。
5. **上游模型、对象存储或外部服务**：区分网络连接、服务端处理、流式首包和完整响应。

用 `request_id` 或 trace id 将这些片段串起来。只有知道慢在进入执行前、数据库里，还是外部模型等待，优化才不会变成猜测。

## 常见的四类长尾原因

### 1. 请求排队被误认为业务执行慢

同步线程池被长轮询、SSE 或文件解析占满时，新请求可能还没有开始执行，就已经消耗了大部分耗时。此时应用日志里的函数耗时看起来不高，但客户端看到的 P95 很高。

排查方法：比较网关记录的总耗时和应用内部 `handler` 耗时；如果两者差距明显，再看线程池队列长度、连接池等待和长连接数量。

优化方向：将长连接等待与普通 API 使用的执行资源隔离；给文件解析、模型调用和管理端采集设置独立并发上限；对不影响用户体验的状态查询降低频率。

### 2. 数据库慢查询或连接等待

查询条件缺少索引、一次返回太多历史记录、事务持锁时间过长，都会让少数请求极慢。连接池过小也会表现为“数据库偶尔很快，偶尔突然很慢”。

不要只看 SQL 平均耗时，至少记录 P50、P95、P99、扫描行数、返回行数和连接等待时间。先修正最常出现且最影响长尾的查询，再讨论更复杂的缓存。

### 3. Redis 历史扫描和重复轮询

每次状态刷新都扫描整段事件流，或者多个页面、多个标签页同时轮询同一状态，会造成命令量和序列化开销随用户数线性放大。即使单次命令很快，累计竞争也会推高其他接口的尾延迟。

优化时要区分“确实需要实时更新”的请求与“只是为了确认页面还开着”的请求。状态快照、有界增量读取、退避和面试结束后的及时停止，通常比单纯提高机器规格更有效。

### 4. 上游模型或外部服务的尾延迟

模型首包慢、网络抖动、重试叠加，都会直接反映到 API P95。此时不能把等待时间算作本地业务执行耗时后再误判为数据库问题。

建议记录上游请求开始、首包、完成、重试次数和最终状态。对非关键的附加能力采用超时、降级或异步处理，避免把可选功能的等待串到普通快答链路。

## 一套可执行的排查顺序

1. 固定一个 5–15 分钟窗口，导出按路由分组的请求数、P50、P95、P99 和 5xx。
2. 取最慢的两个路由，抽样 20–50 条 trace，标记排队、数据库、Redis、上游和序列化耗时。
3. 对照请求量变化，确认是否有页面心跳、状态轮询或后台任务在同一时间放大。
4. 先处理占比最高且可低风险验证的一段，重新观察同一个时间窗口和同一组请求。
5. 保留优化前后证据，确认用户链路的成功率、首字节时间和回答完整性没有变差。

## 不建议的处理方式

- 只看平均耗时，忽略 P95/P99；
- 看到 P95 升高就重启，重启后没有留下证据；
- 只扩大 CPU，却不确认是不是排队、重复轮询或慢查询；
- 把合成压测结果写成线上 SLA；
- 为了降指标直接关闭用户需要的状态反馈。

## FAQ

### API P95 升高一定是服务器配置不够吗？

不一定。配置不足会放大排队和竞争，但重复请求、数据库连接等待、外部模型尾延迟同样常见。先分段测量，再决定扩容还是改逻辑。

### 一个用户测试也会让 P95 变高吗？

会。P95 是时间窗口内请求样本的统计结果。一个页面打开多个标签、伴随程序与网页同时查询，或者单次模型请求很慢，都可能在低并发时制造明显长尾。

### 应该看 P95 还是 P99？

P95 适合观察大多数用户能感受到的长尾，P99 更适合发现极端卡顿和偶发超时。两者应结合请求量和成功率一起看。

## 结论与下一步

API P95 高的核心不是“找一个神奇参数”，而是把总耗时拆成可验证的片段。先按路由和来源定位，再用 trace 区分排队、数据库、Redis、上游和网络，最后用同一口径验证优化结果。
